## 1. 背景：为何不能只修 Gemini

当前实现路径是 **「在 `geminiService` 里补复合记账」**——能跑通 Vertex 生图，但带来四类架构债：

| 问题 | 表现 |
|------|------|
| **供应商耦合** | `buildAiWorkerProxyUsageDrafts`、`usageBillingSku` 全是 Gemini 启发式；OpenAI/ToAPIs/腾讯 3D 无等价路径 |
| **写入口分散** | `geminiService` / `tripoService` / `unifiedAiGateway` 各自 `recordUsageEvent`，无统一契约 |
| **四环未关联** | 步骤时间线、工作流审计、`workflow_task_events`、`usage_events` 仅靠 `meta.taskId` 弱链；`auditLogId` 列从未写入 |
| **读写混杂** | `usageApi.ts` 同时承担价目重算、分组展示、BYOK 判定；UI 与领域规则缠在一起 |

**结论**：后续改动应收敛到 **分层 + 模块化 + 规范关联键**，禁止继续在单个 adapter 内堆叠计费分支。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **分层对齐** | 执行、可观测、计费、存储、展示五层职责清晰，单向依赖 |
| **供应商无关** | 计量内核不认 Gemini/OpenAI；只认规范化 `MeterReading` |
| **四环正交** | 时间线 / 审计 / 任务事件 / 用量 **各写各表**，通过关联平面 JOIN，不合并存储 |
| **单写出口** | 每环一个 facade，禁止业务组件直接碰 store / `localStorage` / `auth-api` |
| **可渐进迁移** | 先抽内核、再迁供货商、最后统一 UI 与配额；允许短期双写 |

## 3. 概念分层（自上而下）

```text
┌─────────────────────────────────────────────────────────────────┐
│ L5 展示层 Presentation                                         │
│  Admin：Usage / TaskEvents / AuditActivity（员工权限）          │
│  用户：步骤时间线（成功路径）；审计 Activity（R0 后）           │
│  ❌ 普通用户不展示美元用量（Phase 1 已收口到 Admin）            │
└───────────────────────────────┬─────────────────────────────────┘
                                │ 只读 Query API / 派生读模型
┌───────────────────────────────▼─────────────────────────────────┐
│ L4 关联平面 Correlation                                         │
│  correlationId（= workflow taskId）                              │
│  + projectId, assetId, actionType, auditEventId?, resultKey?    │
└───────────────────────────────┬─────────────────────────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
┌───────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ L3 可观测四环  │     │ L2 计量管线      │     │ L1 执行编排      │
│ Timeline 派生 │     │ Metering Pipeline│     │ WorkflowSection │
│ Audit 环      │     │ normalize→sku→$  │     │ runTask 分支    │
│ TaskEvents    │     │ → emit usage     │     │ capabilityExec  │
│ UsageEvents   │     │                  │     │ unifiedAiGateway│
└───────┬───────┘     └────────┬─────────┘     └────────┬────────┘
        │                      │                        │
        └──────────────────────┼────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ L0 契约层 Contract（shared/）                                    │
│ MeterReading, UsageEmitDraft, CorrelationContext, BillingSkuRef   │
│ PriceCatalogEntry, AuditEventEnvelope, TimelineStepView           │
└─────────────────────────────────────────────────────────────────┘
```

**依赖规则（硬约束）**

1. L1 只能向下调用 L2/L3 的 **facade**，不得 import store 或 `usageApi` 格式化。
2. L2 不得 import `geminiService` / `openaiAdapter`；adapter 只 **上报** `MeterReading`。
3. L3 各环 **禁止互相 import**；只共享 L0 类型与 L4 关联上下文。
4. L5 只消费 Query 接口，不得在组件内重算价目（价目重算属于 L2）。

## 4. 四环定义与边界（正交存储）

| 环 | 回答的问题 | 写触发 | 存储 | 用户可见 |
|----|-----------|--------|------|----------|
| **P0 步骤时间线** | 资产上正式提交过什么？ | `results`/`resultMeta` 写入 | 项目 bundle（云同步） | ✅ 工作流内 |
| **P2 工作流审计** | 失败/拒绝/导出/敏感操作？ | `appendWorkflowAuditEvent` | 本机环 + 可选上云 | R0 后 Activity |
| **TaskEvents** | 全站任务执行遥测？ | `RUN_TASK_*` 同步 | `workflow_task_events` | Admin |
| **Usage** | 花了多少计量/估算美元？ | AI/3D/视频 **成功完成点** | `usage_events` | Admin（`usage.read`） |

**关键原则**：四环 **不合并成一张大表**。产品语义不同、保留期不同、合规字段不同。

## 5. 关联平面（Correlation Plane）

所有环写入时携带同一 **关联包**（`CorrelationContext`）：

```ts
type CorrelationContext = {
  correlationId: string;      // = WorkflowPendingTask.id（任务 ID）
  projectId?: string;
  assetId?: string;
  actionType?: string;        // 预设/步骤 id（现 workflowStepId 字段存的就是它）
  auditEventId?: string;      // appendWorkflowAuditEvent 返回的 id
  resultKey?: string;         // 时间线条目（成功落盘后补写，可选）
  registryId?: string;        // 输入口 SKU
  channelId?: string;         // 输出口
};
```

**写入顺序（runTask 一次执行）**

```text
1. setCorrelationContext(ctx)          // 替代现有 usageRecordContext
2. appendWorkflowAuditEvent(...)       // 失败时；成功可选轻量事件
3. gateway.invoke() → MeterReading
4. meteringPipeline.emit(reading, ctx)
5. syncWorkflowTaskEvent(RUN_TASK_*)   // 已有
6. （成功）results 写入 → 时间线派生   // 已有
```

**待修命名债**：`usage_events.workflow_step_id` 实际存 `actionType`，读模型层映射为 `actionType`，避免 UI 显示「步骤」却指向预设 id。

## 6. 计量管线（L2）— 供应商无关内核

### 6.1 统一中间表示：`MeterReading`

```ts
type MeterReading = {
  provider: string;           // vertex | openai | tripo | ...
  modality: 'text' | 'image' | '3d' | 'video' | 'task';
  parts: MeterPart[];         // 可多条：input_token, output_token, output_image, task, ...
  rawUsage?: unknown;         // 上游原始 usage，不入库 prompt
  confidence: 'exact' | 'estimated';
};

type MeterPart = {
  kind: 'input_token' | 'output_token' | 'output_image' | 'task' | 'second';
  quantity: number;
  unit: string;
};
```

### 6.2 管线阶段（纯函数，可单测）

```text
MeterReading
  → normalizeMeterReading()      // 校验、合并、兜底
  → resolveBillingSku()          // registryId × modality × channel → billingSku
  → splitUsageDrafts()           // 复合拆分（生图 input/output）；策略按 modality 而非供应商
  → estimateCostUsd()          // 价目表；image output token 用 imageOutputPer1m
  → buildUsageEmitDrafts()     // idempotencyKey、meta.usagePart
  → usageEmitFacade.emit()     // POST /api/usage/events
```

### 6.3 Adapter 职责（极薄）

| Adapter | 只做 |
|---------|------|
| `ai-worker-proxy` / `extractUsageMetadata` | 响应 → `MeterReading` |
| `openaiAdapter` | `usage` 字段 → `MeterReading` |
| `tripoService` | 建任务 → `{ modality:'3d', parts:[{task:1}] }` |
| `tencentService` | 同上（待接） |

**禁止**：在 adapter 内调用 `recordUsageEvent`、查价目表、拼 `billingSku`。

### 6.4 挂载点：唯一网关钩子

```text
unifiedAiGateway.traceUnifiedAiCall 包装层（或 invoke 尾部）
  → adapter 返回 { result, meterReading? }
  → if meterReading: meteringPipeline.emit(meterReading, getCorrelationContext())
```

`geminiService.bulkProxyGenerateContentAsync` 退化为 **Gemini channel 的 transport**，不再拥有记账所有权。

### 6.5 价目表与 SKU 注册（与模型中心对齐）

扩展 `shared/usageBillingCatalog.ts` 为 **按 modality 分族**，而非按供应商文件分裂：

| billingSku 族 | 示例 | 价目维度 |
|---------------|------|----------|
| `llm.{vendor}.{tier}` | `llm.gemini.flash`, `llm.openai.gpt4o` | input/output token |
| `image.{vendor}.{tier}` | `image.gemini.pro`, `image.openai.gpt2` | input token, image output token, per-image fallback |
| `3d.{vendor}.task` | `3d.tripo.task` | per task |
| `video.{vendor}.task` | `video.workflow.task` | per task |

`resolveBillingSku(registryId, modality, channelId)` 集中在一处，**模型注册表**提供默认映射，运营可覆盖（与 `bindingOverrides` 同模式）。

## 7. 模块目录规划（目标态）

```text
shared/
  observability/           # L0 契约
    correlation.ts
    meterReading.ts
    usageEmit.ts
  usageBillingCatalog.ts   # 价目种子（保留）

services/observability/
  correlationContext.ts    # 替代 usageRecordContext，四环共用
  metering/
    normalize.ts
    resolveBillingSku.ts
    splitDrafts.ts          # 从 usageCost 迁出；modality 策略
    estimateCost.ts
    pipeline.ts             # emit 编排
    adapters/
      gemini.ts             # usageMetadata → MeterReading
      openai.ts
      tripo.ts
  usageEmitFacade.ts        # 唯一 POST /api/usage/events
  rings/
    audit/                  # 薄封装 workflowAuditEvents
    taskEvents/             # 薄封装 sync
    timeline/               # 读模型 helper（已有 workflowStepTimeline）

services/usageApi.ts        # 仅 L5 读模型 + 格式化（不再 estimate 业务规则）
```

| 现有 | 目标 |
|------|------|
| `usageRecordContext.ts` | `correlationContext.ts` |
| `usageCost.buildAiWorkerProxyUsageDrafts` | `metering/splitDrafts.ts`（modality=image） |
| `usageBillingSku.ts` | `metering/resolveBillingSku.ts` |
| `geminiService.recordAiWorkerProxyUsage` | 删除；改 `metering/adapters/gemini.ts` + pipeline |

## 10. 分阶段落地（禁止跳步）

### Wave 0 — 契约与关联（1 周，无用户可见变化）

- [ ] 新增 `shared/observability/*` 类型
- [ ] `correlationContext` 替代 `usageRecordContext`；`WorkflowSection.runTask` 改 import
- [ ] 文档化 `workflow_step_id` = `actionType` 映射
- [ ] 单测：关联包透传

### Wave 1 — 计量内核抽离（1～2 周）

- [ ] `metering/pipeline.ts` + `splitDrafts`（迁 Gemini 复合逻辑）
- [ ] `geminiService` 删除 `recordAiWorkerProxyUsage`；proxy 完成点改报 `MeterReading`
- [ ] **行为回归**：现有 Gemini 复合 `:in`/`:out` 事件字节级一致
- [ ] 价目表补 `imageOutputPer1m`（已修）纳入 `estimateCost` 模块

### Wave 2 — 多供货商接入（按供货商并行，但走同一管线）

- [x] OpenAI：`openaiAdapter` 解析 `usage` → `metering/adapters/openai.ts`
- [x] 价目表：`llm.openai.*`, `image.openai.*`
- [x] ToAPIs / VectorEngine：Gemini 形态 `wrapGeminiClientWithChannelMetering` + `emitGeminiChannel`
- [x] 腾讯 3D：`3d.tencent.pro` / `3d.tencent.rapid` + `tencent-3d:{jobId}`
- [ ] 验收表：供货商矩阵 **每行** 有「MeterReading 样例 + 单测」

### Wave 3 — 关联与 Admin 读模型（2 周）

- [x] `auditEventId` 写入 `usage_events`（`audit_log_id` 列 + `meta.auditEventId`）
- [x] `GET /api/admin/observability/trace?correlationId=`
- [x] Admin Usage ↔ TaskEvents 互链（任务 ID 深链 + 执行记录筛选）
- [x] 后端 `usage/summary` 仅 Admin；用户 API 关闭或 403（`GET` 需 `usage.read`；`POST /api/usage/events` 记账保留）

### Wave 4 — 准入统一（Phase 2 商业）

- [ ] `checkAndConsume` 替换 `trial-gemini`
- [ ] 用户可见 credits（若产品需要）走 L5 新组件，**不复用** Admin 表格

## 11. 反模式（代码评审一票否决）

1. ❌ 在 `geminiService` / `openaiAdapter` 内 `recordUsageEvent`
2. ❌ 在 UI 组件 `computeReferenceCostUsd` 业务分支
3. ❌ 为单个供应商新增 `billingSku` 而不更新 `resolveBillingSku` 注册表
4. ❌ 把审计环与 usage 合并存储「方便查询」
5. ❌ 无 `correlationId` 的 usage 事件（除系统级任务外）
6. ❌ 继续在 `usageApi.ts` 增加供应商特殊格式化
