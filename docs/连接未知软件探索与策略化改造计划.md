# 连接未知软件探索与策略化改造计划

状态：可循环执行  
目标读者：AI Agent、Local Companion 开发者、Copilot 连接能力维护者  
配套状态文档：`docs/连接改造执行状态.md`

## 0. 执行总览

这不是产品愿景文档，而是给 AI Agent 循环执行的开发任务书。Agent 每次恢复执行时，应把本文当作“任务定义”，把 `docs/连接改造执行状态.md` 当作“事实账本”。

每一轮只做一个可验证增量：

```text
读状态 -> 选最小任务 -> 改最少文件 -> 跑明确检查 -> 写证据 -> 判断继续或停止
```

如果 agent 发现代码已经部分实现，不能直接跳过；必须补齐该任务的自动验证、人工验收状态和执行记录。没有证据的完成不算完成。

## 0.1 Agent 执行入口

本文件是开发计划，`docs/连接改造执行状态.md` 是任务状态的唯一真相。继续执行时不要只看本文里的 `pending` 字样，必须先读取状态文档，找到第一个未完成任务。

每轮 agent 的最小工作单元是一个 `UNKNOWN-PX-XXX` 任务。完成一个任务后必须写入状态文档，再决定是否继续下一个任务。

恢复执行时先做四件事：

1. 读取本文档，确认产品心智、非目标和禁止链路。
2. 读取 `docs/连接改造执行状态.md`，确认已完成任务、当前任务、最近失败和下一任务。
3. 读取当前任务列出的源码和测试文件，不凭记忆修改。
4. 跑当前任务的 focused checks；若恢复检查失败，先判断是否与当前任务相关。

状态判断规则：

1. 如果状态文档已有某任务 `completed` 记录，以状态文档为准。
2. 如果本文任务清单仍写 `状态：pending`，但状态文档显示已完成，不要重复实现，只做必要的复核和补证据。
3. 如果代码看起来已实现但状态文档缺少证据，补测试和执行记录后再继续。
4. 如果用户提出新的更高优先级问题，在状态文档记录插队原因，再按同样格式拆成可验证任务。

## 1. 核心产品心智

连接系统的默认心智必须从“选择一个已知宿主”改成：

> 给我一个本机软件，我先把它当未知对象探索；如果命中已验证策略，就快速连接；如果没有命中，就生成可验证的连接策略草稿，并让 Copilot 在安全边界内持续尝试、失败、切换、沉淀。

所有软件一开始都应被视为未知。Unreal、Maya、Photoshop、Blender 只是已经验证过部分策略的样本，不是产品流程前提。已知 driver 是快捷策略，不是世界模型。

### 1.1 产品原则

1. 用户给的是“一个本机软件”，不是“一个预置宿主类型”。
2. 系统先收集事实，再选择策略；不能先按名称套模板。
3. driver 只提供已验证策略捷径，不能决定产品主流程。
4. 一个软件可以有多条策略，一条失败后应自动切换下一条。
5. 真实 probe 前不能显示已连接。
6. 本地探索可以频繁迭代，云端版本只能沉淀 verified strategy。
7. Copilot 的职责是围绕同一个连接对象持续修复，而不是每次重新创建。
8. 新软件接入应扩展 registry/provider/driver，不应改生命周期分支。

## 2. 目标

建立“未知软件优先”的连接架构，使用户可以通过拖入快捷方式、选择可执行文件、识别运行中进程或直接对话，让系统创建一个长期存在、可探索、可修复、可升级的本地连接。

### 非目标

1. 不一次性手写所有软件 driver。
2. 不恢复旧的 62 个宿主中心作为默认产品入口。
3. 不要求用户先选择技术模板。
4. 不允许 Copilot 任意执行 shell、任意写系统目录、任意杀进程。
5. 不把“发现 exe”“安装文件成功”“看起来像某软件”当作连接成功。
6. 不把本地探索草稿自动发布为云端正式能力。

## 3. 当前约束

1. 仓库可能存在用户或上一轮 agent 的未提交改动，执行前必须先观察，不得回滚无关改动。
2. `capabilityLifecycle.ts` 不应再新增具体软件分支。
3. 连接页不应维护本地 driver/software 关键词兜底识别。
4. `connected` 只能来自真实 probe 成功，安装完成不等于连接成功。
5. Unreal 当前已暴露项目插件和引擎插件两种合理安装位置，后续不能再写死单一路径。
6. 前端 TSX/JSX 不新增原生 `<select>`，使用现有自定义下拉组件。
7. 运行时代码位于 `local-companion/` 或 `companion-desktop/` 时，完成相关代码改动后需要执行 `npm run restart:local-companion`。
8. 文档只定义开发执行路线，不替代每轮真实代码阅读和测试。
9. 旧“宿主中心”文档、旧 62 宿主 catalog 和 `ac.companion.host_bridge.*` 只能作为 legacy recovery/debug 参考，不能作为新连接页的产品入口。
10. 如果用户拖入快捷方式、exe 或通过对话添加软件，默认都进入 `software_connection` 能力包对象，不进入工具流、工具架或 Workbench 文本资产。

## 4. 完成定义

全部满足才算完成：

1. 新建软件连接默认进入 `discovery_pending` 或 `exploring`，而不是先按软件名进入某个 driver。
2. 后端有 `ConnectionFacts` 类型、标准化函数和事实收集接口。
3. 后端有 `ConnectionStrategy` 类型和通用 strategy registry。
4. 未知软件即使没有 driver，也能生成 `StrategyDraft`。
5. 已知 driver 可声明多个策略，至少 Unreal 支持 `project_plugin` 与 `engine_plugin`。
6. Copilot 的 `connection_loop_run` 能根据失败原因切换到下一个候选策略。
7. 策略失败必须写入事件，包含 `strategyId`、`failureClass`、`nextCandidateStrategy`。
8. probe 成功前永远不能标记为 `connected`。
9. 云端只允许发布已验证 strategy，本地探索草稿不污染正式版本。
10. 连接页能展示 facts、当前策略、候选策略、失败原因和下一步。
11. 自动测试证明新增策略类型不需要修改 `capabilityLifecycle.ts`。

## 5. 目标架构

```text
用户输入软件名 / exe / 快捷方式 / 运行中进程
  -> 创建 CapabilityPackage(type=software_connection)
  -> ConnectionDiscovery 收集事实
  -> StrategyRegistry 生成候选 ConnectionStrategy[]
  -> 命中已验证 driver：推荐 verified strategy
  -> 未命中：生成 StrategyDraft
  -> Copilot connection_loop_run 执行当前策略
  -> 失败：记录 failureClass，选择下一策略
  -> probe 成功：标记 connected，可沉淀为 verified strategy
```

禁止链路：

```text
用户说添加软件
  -> 前端猜测具体软件
  -> 单一 driver 写死安装目录
  -> 失败后只能让用户换路径
```

## 6. 核心概念

### 6.1 ConnectionFacts

连接事实是系统和 Copilot 探索未知软件的共同输入。事实只能来自可追踪来源，例如快捷方式解析、进程枚举、文件结构探测、版本文件、用户明确选择。

建议字段：

- `displayName`
- `inputPath`
- `shortcutPath`
- `executablePath`
- `processName`
- `version`
- `installRoot`
- `candidateProjectDirs`
- `candidateScriptDirs`
- `candidatePluginDirs`
- `candidateConfigDirs`
- `detectedProtocols`
- `confidence`
- `evidence`

### 6.2 ConnectionStrategy

连接策略是可执行、可验证、可失败、可切换的最小连接方案。

建议字段：

- `id`
- `label`
- `kind`
- `risk`
- `requiresUserDirs`
- `installPlan`
- `probePlan`
- `uninstallPlan`
- `safetyBoundary`
- `confidence`
- `verified`
- `failureClass`

首批通用策略类型：

- `existing_process_probe`
- `project_plugin`
- `engine_plugin`
- `script_folder`
- `startup_script`
- `command_port`
- `http_probe`
- `heartbeat_file`
- `extension_panel`
- `manual_bridge_script`

### 6.3 SoftwareBridgeDriver

driver 不再代表“某软件的唯一写死实现”，而是：

- 匹配事实。
- 声明已验证或计划中的策略。
- 调用通用 strategy executor。
- 记录策略级结果。

未知软件可以没有 driver，只拥有 strategy draft。

### 6.4 StrategyDraft

当 registry 未命中 verified strategy 时，生成 `StrategyDraft`：

- `connectionId`
- `facts`
- `candidateStrategies`
- `recommendedNextStrategy`
- `questionsForUser`
- `blockedReason`
- `requiredEvidenceToVerify`

StrategyDraft 只属于当前连接对象，不能自动发布到云端。

## 7. Agent 循环协议

每一轮 agent 必须按以下顺序执行：

1. Observe：读取本文档、`docs/连接改造执行状态.md`、相关源码和最近测试结果。
2. Select：选择第一个 `pending` 且依赖已完成的任务。
3. Scope：只打开该任务允许修改的文件；如果必须扩大范围，先在执行记录写明原因。
4. Act：做满足任务目标的最小改动。
5. Verify：先跑任务列出的 focused checks，再跑必要回归。
6. Record：把结果追加到 `docs/连接改造执行状态.md`。
7. Continue or Stop：检查通过则继续下一个任务；遇到真实阻塞、权限需求或用户指令才停止。

每轮执行的固定输出必须包括：

1. 本轮选择的任务编号和选择理由。
2. 实际改动文件。
3. 自动验证命令与结果。
4. 人工验收是否执行；未执行必须写 `pending` 和原因。
5. 残留风险。
6. 下一任务编号。

禁止事项：

1. 不用“看起来已经可以”替代测试。
2. 不用新增 UI 文案掩盖后端状态或策略缺失。
3. 不把缺少真实软件的人工验收伪造为通过。
4. 不为了让流程继续而把 probe 失败写成 connected。
5. 不把本地策略草稿发布为云端正式策略。

### 7.1 每轮工作票

Agent 开始执行任意任务前，先在自己的工作记录里形成以下工作票；如果任一项无法填写，应先补观察，不要直接改代码。

```markdown
任务编号：
选择理由：
依赖状态：
允许修改文件：
预计不修改文件：
自动验收命令：
人工验收要求：
风险边界：
```

任务完成后，工作票必须变成状态文档中的执行记录。执行记录不是总结，而是下一个 agent 能继续工作的恢复点。

### 7.2 循环继续条件

满足以下条件时，agent 可以自动继续下一任务：

1. 当前任务 focused checks 全部通过。
2. 状态文档已追加执行记录。
3. 没有新增产品决策问题。
4. 没有需要用户授权、登录、管理员权限或真实软件操作的阻塞。
5. 下一任务的依赖已经完成。

出现以下情况必须停止并说明：

1. 同一类失败连续三轮无法修复。
2. 需要用户在真实软件里登录、安装、重启或确认高风险目录。
3. 需要扩大 Copilot 权限到当前安全边界之外。
4. 自动测试通过但人工验收失败，且失败来自真实产品行为。

## 8. 任务选择规则

1. 永远从编号最小、状态为 `pending`、依赖已完成的任务开始。
2. 如果当前任务自动验证失败，最多连续修复三轮；三轮仍同类失败则按阻塞规则记录。
3. 不跳到 UI 任务来掩盖后端策略或状态模型缺失。
4. 不为了通过测试把真实 probe、安装或发布判断降级为假成功。
5. 如果发现已有代码已完成某任务，仍要补齐测试和执行记录，再将任务记为完成。

## 9. 阻塞规则

1. 缺少真实软件时，自动测试继续，人工验收记为 pending。
2. 需要用户确认高风险目录写入、管理员权限、软件账号登录时，停止并说明最小需要动作。
3. 未知软件探索不得扩大到任意 shell，只能使用白名单 discovery 能力。
4. 单一策略失败不等于连接失败，必须记录失败并评估下一个候选策略。
5. 所有候选策略失败时，连接状态为 `needs_user_action`，并列出最小问题清单。
6. 同一任务连续三次同类失败后，记录为 blocked，不临时绕过安全边界。
7. 无关检查失败时，记录失败摘要和无关理由；focused checks 通过即可继续。

## 14. 每轮恢复检查

每次 agent 继续执行时先做：

```powershell

```

再检查：

```powershell
rg -n "photoshop|blender|maya|unreal" local-companion/src/capabilities/capabilityLifecycle.ts

```

要求：

1. `capabilityLifecycle.ts` 不出现具体软件分支。
2. Copilot 提示不要求用户选择技术模板。
3. 若恢复检查失败，先判断是否与当前任务相关；相关则修复，不相关则记录并继续 focused task。

恢复检查不等于最终验收。恢复检查只回答“当前是否能继续执行”；最终验收必须执行第 15 节审计问题，并把证据写入状态文档。

## 15. 最终架构审计问题

完成后必须逐条回答：

1. 新软件是否默认按未知对象创建，而不是先匹配已知宿主？
2. 未知软件是否能生成 facts 和 candidate strategies？
3. 已知 driver 是否只是 verified strategy shortcut？
4. 一个软件是否可以拥有多个策略？
5. 一个策略失败后，Copilot 是否能切换下一个策略？
6. 所有策略失败时，是否进入 `needs_user_action` 并给出最小问题清单？
7. probe 成功前是否永远不会 `connected`？
8. 新增策略类型是否无需修改 `capabilityLifecycle.ts`？
9. 云端是否只保存 verified strategy？
10. 连接页是否让用户看懂探索、策略、失败和下一步？

只有以上问题全部回答“是”，本改造才算完成。
