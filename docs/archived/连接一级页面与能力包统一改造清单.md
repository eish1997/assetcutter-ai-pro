# 连接一级页面与能力包统一改造清单

> **不要当待执行任务书（2026-08-25）。** 连接一级页与能力包主线已落地。现行口径：[`架构宪章-本地壳大楼租户.md`](./架构宪章-本地壳大楼租户.md)（通讯室）、[`连接对象卡片实现规格.md`](./连接对象卡片实现规格.md)。

状态：历史改造清单（连接页已存在）  
目标：新建本地壳一级页面“连接”，参考 PI 的轻内核、强扩展思想，把本机软件连接、工具、工具流统一为可通过对话创建、验证、运行、持续修改、提交云端和切换版本的能力包。

## 1. 核心判断

当前“宿主中心”的 62 个宿主列表已经证明了真实软件连接的方向，但它也带来了明显冗余：大量宿主专用 UI、安装器样板、状态分支、云端版本分支和 Copilot 工具分支。继续把 62 个宿主作为新系统的首要迁移对象，会让重构从第一天就被旧结构牵引。

因此产品层面应升级为：

> 左侧导航一级页面：连接。

新“连接”页面不直接继承旧宿主中心的大列表。旧 62 宿主先从新主线中移除或隐藏，作为 legacy 参考、真实连接样例和可回收能力池。新系统从能力包模型开始：先让用户通过对话创建一个连接，再验证、安装、探测、对话修改和提交云端。

核心目标是：

> 不是维护一个越来越大的预置宿主列表，而是让用户和 Copilot 能在统一架构上长出自己的连接、工具和工具流。

## 2. 命名约定

### 2.1 用户可见命名

1. 一级导航：连接。
2. 页面标题：连接。
3. 软件连接分区：本机软件。
4. 桥接安装能力：连接插件或连接脚本。
5. 探测连接：探测连接。
6. 云端版本：云端连接版本。
7. 本地草稿：本地连接草稿。

### 2.2 内部技术命名

Legacy 层短期继续沿用：

1. `host bridge`
2. `bridges`
3. `hostBridgeDefinitions`
4. `hostBridgeDrafts`
5. `hostBridgeCloud`

新主线新增统一抽象：

1. `CapabilityPackage`
2. `capabilityType: software_connection | tool | workflow`
3. `source: builtin | draft | cloud`
4. `lifecycle: create | validate | install | run | probe | uninstall | publish | switch_version`

## 3. PI 对齐原则

1. 轻内核。  
   本地壳只提供能力包运行时、权限边界、对象对话、版本治理和真实连接探测，不把每个软件都写成一套产品逻辑。

2. 强扩展。  
   新连接、工具和工具流都以能力包形式存在，可以来自内置、Copilot 草稿、用户本地包或云端版本。

3. 对话生长。  
   用户不选技术模板，只描述目标。Copilot 根据目标创建或修改能力包。

4. 包优先。  
   UI、云端版本、对象对话、安装/运行/探测都围绕能力包，而不是围绕“宿主中心”“工具页”等旧页面概念。

5. 真实信号。  
   软件连接必须来自真实宿主运行信号，不能用文件存在或卡片存在冒充成功。

## 4. 不变原则

1. 不弱化真实连通门禁。文件存在、卡片存在、安装记录存在都不能算连接成功。
2. 不让本地草稿自动污染云端版本。
3. 不让普通用户提交云端或切换云端版本。
4. 不让 Copilot 要求用户选择技术模板。
5. 不允许任意路径写入、任意命令启动、任意进程关闭。
6. 不把旧 62 宿主列表作为新连接页面的默认内容。
7. 不在第一阶段做大规模内部重命名，避免破坏可复用的真实连接代码。

## 8. 阶段 2：能力包最小模型

### 8.1 目标

建立统一抽象，让软件连接、工具、工作流都能被描述为能力包。新连接页面直接消费能力包，不消费旧宿主 catalog。

### 8.2 新增模型

```ts
type CapabilityPackage = {
  id: string;
  type: 'software_connection' | 'tool' | 'workflow';
  name: string;
  source: 'builtin' | 'draft' | 'cloud';
  description: string;
  tags: string[];
  version?: string;
  manifest: Record<string, unknown>;
  lifecycle: {
    validate?: string;
    install?: string;
    run?: string;
    probe?: string;
    uninstall?: string;
    publish?: string;
  };
  conversation: {
    sessionId: string;
    contextProvider: string;
  };
  governance: {
    requiresAdminToPublish: boolean;
    requiresRealProbeToPublish: boolean;
    cloudVersioned: boolean;
  };
};
```

### 8.3 修改位置

1. 新增 `local-companion/src/capabilities/capabilityPackages.ts`
2. 新增 `local-companion/src/capabilities/softwareConnectionAdapter.ts`
3. 新增 `local-companion/src/capabilities/toolPackageAdapter.ts`
4. 新增 `tests/capabilityPackages.test.ts`

### 8.4 执行任务

   - 执行：新增类型、校验函数、来源字段。
   - 验证：坏 id、未知 type、缺少 manifest 会失败。
   - 完成：schema 可以表达软件连接、工具、工作流。

2. 软件连接草稿适配为能力包。

## 9. 阶段 3：连接草稿闭环

### 9.1 目标

用新能力包路径跑通一个软件连接：创建草稿、校验、选择本机目录、安装、真实探测、对象对话、卸载。

### 9.2 最小样板

第一批只支持 1 到 3 个连接样板，不恢复 62 个宿主大列表：

1. Photoshop：ExtendScript heartbeat。
2. Blender 或 Maya：Python/命令端口真实连接。
3. Unity 或 Unreal：项目插件连接。

### 9.3 执行任务

1. 创建连接草稿。
   - 执行：Copilot 调用能力包创建接口。
   - 验证：连接页面出现一个本地连接草稿。
   - 完成：用户不需要选择模板。

2. 真实安装。
   - 执行：用户选择目录，系统按包 manifest 写入连接脚本或插件。
   - 验证：错误目录被中文提示纠正。
   - 完成：只写入允许目录。

3. 真实探测。
   - 执行：探测来自 HTTP health、heartbeat、命令端口或插件回调。
   - 验证：未运行软件时失败，运行真实脚本后成功。
   - 完成：文件存在不算连接成功。

4. 对象对话。
   - 执行：每个连接包有独立 session。
   - 验证：对 Photoshop 连接提问时，带上它自己的目录、日志、probe 状态。
   - 完成：不同连接和工具对话不串线。

### 9.4 完成判定

1. 对话创建一个连接草稿成功。
2. 连接页面只显示用户创建或云端同步的连接包。
3. 安装、探测、卸载走能力包生命周期。
4. 探测成功来自真实软件信号。
5. 对象对话可持续修改该连接。

## 10. 阶段 4：工具与连接共用生命周期

### 9.1 目标

2. `validate`

3. 统一对象对话入口。

   - 验证：软件连接和工具都能打开独立对话。

4. 统一云端发布前置门禁。

## 11. 阶段 5：云端版本统一

### 11.1 目标

能力包共用管理员提交、历史版本、激活版本和团队同步。软件连接、工具、工具流使用同一套版本治理模型。

### 11.2 执行任务

1. 统一发布门禁。
   - 执行：根据 package governance 判断管理员、版本说明、真实 probe。
   - 验证：软件连接未真实探测不能发布；工具按工具门禁发布。
   - 完成：发布规则不散落在不同 UI 分支。

2. 统一云端版本存储。
   - 执行：云端版本记录 `packageId`、`type`、`manifest`、`versionId`、`active`。
   - 验证：工具和连接都能发布两个版本并切换。
   - 完成：版本切换只切换云端已有版本。

3. 团队同步。
   - 执行：普通用户同步云端能力包。
   - 验证：普通用户可使用云端连接/工具，但不能提交或切版本。
   - 完成：权限边界不回退。

### 11.3 完成判定

1. 能力包云端历史版本可用。
2. 软件连接发布要求真实 probe。
3. 普通用户不能发布或切换版本。
4. 本地草稿不污染云端版本。

## 12. 阶段 6：Legacy 能力回收

### 12.1 目标

从旧 62 宿主中按需回收真实连接样例，而不是批量迁移。每次只把用户真正需要的软件变成新能力包样板。

### 12.2 执行规则

1. 不恢复 62 个默认卡片。
2. 用户或产品明确需要某软件时，再从 legacy 安装器回收能力。
3. 回收时必须改造成能力包 manifest + lifecycle。
4. 回收后进入新连接页面的是能力包，不是旧 host card。
5. 每回收一个软件，必须有真实连接验证路径。

### 12.3 第一批建议

1. Photoshop：覆盖 Adobe 脚本类。
2. Blender 或 Maya：覆盖 DCC Python/命令端口类。
3. Unity 或 Unreal：覆盖项目插件类。

### 12.4 完成判定

1. 旧代码只作为实现参考。
2. 新页面只显示能力包。
3. 每个回收连接都能通过对话继续修改。
4. 不以回收数量作为阶段成功指标。

## 13. 阶段 7：Copilot 创建入口收敛

### 13.1 目标

用户通过自然语言创建能力，不需要先知道自己要创建工具、软件连接还是工作流。

### 13.2 目标体验

用户可以说：

1. “做一个随机选择工具。”
2. “添加 Photoshop 连接。”
3. “把 Blender 导出 FBX 和上传流程串成一个工具流。”
4. “这个 Photoshop 连接探测失败了，帮我修一下。”

Copilot 应自动判断能力类型，并调用对应生命周期。

### 13.3 执行任务

## 21. Loop Engine 验收标准

### 21.1 Loop Engine 定义

这里的 Loop Engine 不是单次创建工具或连接，而是一条可持续循环：

> 用户意图 -> 能力包草稿 -> 执行/安装/运行 -> 观察结果 -> 判断问题 -> 对话修复 -> 再执行 -> 通过后沉淀版本。

它要求系统能把每一次运行结果、错误日志、探测状态、用户反馈重新喂回当前能力包的对象对话中，让 Copilot 持续修改同一个对象，而不是每次都重新生成一份新东西。

### 21.2 Loop Engine 必须具备的能力

1. 独立对象上下文。  
   每个能力包都有自己的 session、manifest、安装记录、运行日志、probe 结果和版本状态。

2. 可观察。  
   运行失败、安装失败、探测失败、权限失败、目录错误都必须记录为结构化事件，而不是只弹出一次性提示。

3. 可反馈。  
   用户在对象对话中说“刚才失败了”“入口找不到”“继续优化”，Copilot 能读取该能力包最近的事件和状态。

4. 可修改。  
   Copilot 修改的是当前能力包草稿或当前本地开发版本，不新建无关资产，不污染云端版本。

5. 可再执行。  
   修改后能重新安装、运行、探测，并把新结果继续写回该能力包状态。

6. 可收敛。  
   连续失败时必须给出明确下一步，不能无限循环；需要用户选择路径、打开软件或管理员确认时，必须停下来等待。

7. 可发布。  
   只有通过门禁后，管理员才能把当前能力包提交云端，形成云端历史版本。

### 21.3 P1 Loop 验收

目标：证明单个软件连接能完成一次真实的“失败 -> 修复 -> 再验证”循环。

必须同时满足：

1. 用户通过对话创建 Photoshop 连接草稿。
2. 第一次探测在未运行 Photoshop 脚本时失败。
3. 失败结果写入该连接的对象状态。
4. 用户在 Photoshop 连接对象对话中说“探测失败了，帮我看一下”。
5. Copilot 能指出失败原因和下一步，例如需要在 Photoshop 菜单运行连接脚本。
6. 用户运行脚本后再次探测。
7. 探测成功结果写回同一个连接对象。
8. 对象对话能回答“刚才为什么失败、现在为什么成功”。

完成判定：

该连接没有新建第二个 Photoshop 草稿，没有生成文本资产，没有把失败状态误提交云端。

### 21.4 P2 Loop 验收

目标：证明工具能力包也能进入同样的循环。

必须同时满足：

1. 用户通过对话创建一个随机选择工具。
2. 工具第一次运行出现一个可复现问题，或通过测试构造一个失败状态。
3. 失败日志进入该工具对象上下文。
4. 用户在工具对象对话中要求修复。
5. Copilot 修改当前工具能力包。
6. 再次运行通过。
7. 修复记录进入本地草稿历史，但不自动形成云端版本。

完成判定：

工具修复不进入 Workbench 文本资产，不影响其它工具，不要求用户理解文件结构。

### 21.5 P3 Loop 验收

目标：证明工具流能力包可以串联多个能力，并在中间失败时定位到正确对象。

必须同时满足：

1. 用户通过对话创建一个工具流，例如“Photoshop 批处理后导出并交给另一个工具处理”。
2. 工具流运行时至少包含两个步骤。
3. 某一步失败时，系统能定位失败属于哪个能力包或哪个步骤。
4. 用户在工具流对象对话中要求修复。
5. Copilot 能选择修复工具流本身，或跳转到对应子能力对象对话。
6. 修复后重新运行工具流。
7. 新结果写回工具流对象状态。

完成判定：

工具流不是一次性脚本，而是可观察、可修改、可再运行的能力包。

### 21.6 Loop Engine 反例

以下情况都不算通过：

1. Copilot 每次失败后重新生成一个新工具或新连接。
2. 失败原因只显示在弹窗里，没有进入对象状态。
3. 用户说“继续修”，Copilot 不知道刚才运行了什么。
4. 修改后不能再次运行或探测。
5. 本地调试失败自动污染云端版本。
6. 普通用户可以绕过管理员门禁发布修复版本。
7. 软件连接只因为文件存在就被标记成功。

### 21.7 Loop Engine 最终完成判定

同时满足以下条件，才认为符合 Loop Engine 概念：

1. 软件连接、工具、工具流都能进入对象级循环。
2. 每次循环都有结构化观察结果。
3. 对象对话能读取最近状态并继续修改。
4. 修改作用于同一个能力包。
5. 再执行结果会覆盖或追加到同一对象状态。
6. 成功后可由管理员提交云端版本。
7. 失败时有明确停止条件和用户下一步。
8. 旧 62 宿主不会绕过能力包循环回到默认主线。

## 22. AI Agent 执行协议

### 22.1 目标

本节用于让 AI agent 能按 loop engine 方式持续执行本文档，而不是一次性读完整篇后自由发挥。

执行原则：

1. 每轮只执行一个最小任务。
2. 每轮必须先读取执行状态。

4. 每轮必须记录修改了哪些文件。
5. 每轮必须运行该任务对应的最小验证。
6. 每轮必须更新执行状态。
7. 遇到停止条件必须停下，不允许靠 mock、跳过真实门禁或扩大范围强行完成。

### 22.3 每轮执行流程

4. 复述任务 ID、目标、允许修改文件和验证命令。
5. 只修改该任务允许范围内的文件。

7. 如果验证失败，尝试修复；同一失败最多连续尝试 3 次。
8. 更新执行状态文件。
9. 满足停止条件时停止并说明原因。
10. 通过任务验收后再进入下一任务。

9. 禁止破坏现有工具页、Copilot、云端版本和真实软件验收能力。

### 22.6 全局停止条件

遇到以下情况必须停止：

1. 同一个测试或同一个错误连续 3 次修复失败。
