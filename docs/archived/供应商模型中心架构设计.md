## 1. 背景与结论

当前系统已经有模型注册表、供应商绑定、AI Gateway、供应商 Key 池和前端 BYOK 配置，但它们仍带有历史增量痕迹：有些地方按模型命名，有些地方按能力命名，有些供应商只在前端设置页出现，有些只在管理员 Key 池出现。

后续继续接入火山方舟、即梦、OpenAI、Vertex、ToAPIs、Tripo、腾讯混元、Kling、Runway、音乐供应商等时，不能再按“加一个模型就加一套 UI/Key/路由”的方式扩展。

核心结论：

1. **供应商是供应商，模型是模型，工作台能力是能力。三者必须分层。**
2. **供应商维护自己的模型清单，管理员决定哪些模型发布给工作台。**
3. **工作台只理解固定能力类型：文、图、视频、3D、音乐。**
4. **同一个逻辑模型可以有多个供应路径，用 route/binding 表达。**
5. **Key 池 UI 应按供应商重构，而不是按具体模型或单一能力命名。**

## 2. 概念分层

### 2.1 Provider：供应商

供应商是商业和鉴权主体，例如：

- OpenAI
- Google Vertex
- 火山方舟
- 火山即梦
- ToAPIs
- Tripo
- 腾讯混元
- Kling
- Runway

供应商负责维护：

- 展示名、Logo、官网、控制台、文档、价格页
- 支持能力：text / image / video / 3d / music
- 鉴权方式：API Key、AK/SK、Service Account、OAuth、站点代理
- Key 池：多 Key、优先级、限流、健康状态、冷却
- 模型发现方式：静态、API 扫描、手工录入
- 地域、账号、余额、成本和结算信息

### 2.2 Provider Model：供应商模型

供应商模型是某个供应商真实暴露的模型或 endpoint，例如：

- OpenAI `gpt-image-2`
- 火山方舟 `ep-xxxx`
- 即梦 `jimeng_t2i_v40`
- Tripo 某个 3D 版本

供应商模型负责维护：

- `providerModelId`
- 模型名称、版本、状态
- 能力类型
- 输入输出 schema
- 参数限制
- 价格信息
- 官方文档链接
- 是否已验证可用
- 是否已废弃

### 2.3 Canonical Model：平台逻辑模型

平台逻辑模型是工作台和运营侧展示的稳定模型概念，例如：

- `gpt-image-2`
- `jimeng-image-t2i-v40`
- `tripo-model-v2.5`

它不一定等于某个供应商真实 model id。它用于让用户理解“我选的是什么能力/质量档位”，而不是“我请求了哪个供应商 endpoint”。

### 2.4 Capability / Modality：能力类型

工作台固定理解以下类型：

```ts
type AiModality = "text" | "image" | "video" | "3d" | "music";
```

能力类型决定工作台入口、输入表单、结果卡片和任务生命周期。供应商和模型只是在这些能力下面提供实现路径。

### 2.5 Route / Binding：供应路径

Route 解决“一个逻辑模型可以由多个供应商提供”的问题。

示例：

```ts
{
  canonicalModelId: "gpt-image-2",
  modality: "image",
  routes: [
    { providerId: "openai", providerModelId: "gpt-image-2", priority: 10 },
    { providerId: "volcengine-ark", providerModelId: "ep-xxxx", priority: 20 },
    { providerId: "toapis", providerModelId: "gpt-image-2", priority: 30 }
  ]
}
```

管理员可以启用多个 route，并配置优先级、兜底、套餐可见性和成本策略。

## 3. 目标架构

```text
管理员后台
  -> 供应商中心 Providers
       -> Key 池 / 鉴权 / 官网文档链接 / 健康状态
       -> 模型扫描 / 模型清单 / 成本与价格
       -> 发布开关 / 套餐可见性 / 路由策略

模型中心
  -> Provider Model Catalog
  -> Canonical Model Catalog
  -> Route / Binding / Policy

工作台
  -> 固定能力入口：文 / 图 / 视频 / 3D / 音乐
  -> 读取已发布模型目录
  -> 创建 AI Job

AI Gateway
  -> 根据 modality + canonicalModelId + policy 选择 route
  -> 选择 provider key
  -> 调 provider adapter
  -> 写 job / usage / billing / health
```

## 5. 管理员后台重构建议

### 5.1 从“AI Key 池”升级为“供应商中心”

当前 Key 池不应继续按 `Tripo3D`、`即梦视频` 这样的具体能力命名。目标是按供应商展示：

```text
供应商中心
  OpenAI
  Google Vertex
  火山方舟
  火山即梦
  ToAPIs
  Tripo
  腾讯混元
  Kling
  Runway
```

每个供应商卡片展示：

- 名称、Logo
- 官网 / 控制台 / 文档 / 价格页，一键跳转
- 支持能力标签：文、图、视频、3D、音乐
- Key 数量、ready 数量、冷却数量
- 近 24 小时成功率、429、5xx、平均耗时
- 已发现模型数、已启用模型数、待审核模型数
- 只读模型清单和供应路径清单

### 5.2 供应商详情页

建议标签页：

1. **概览**
   - 官网、控制台、文档、价格页
   - 支持能力
   - 当前状态
   - 成本和调用趋势

2. **Keys**
   - 多 Key 管理
   - 优先级、限流、冷却、恢复
   - 最后成功/失败
   - 健康事件

3. **Models**
   - 从供应商扫描或手工维护的模型
   - 状态：discovered / testing / enabled / deprecated / disabled
   - 能力类型、价格、限制
   - 一键创建或绑定到 canonical model
   - 当前状态：供应商中心已提供只读清单，编辑/绑定动作待后续实现

4. **Routes**
   - 该供应商参与哪些平台逻辑模型
   - 优先级、兜底策略、套餐可见性
   - 当前状态：供应商中心已提供只读路径清单，策略编辑待后续实现

5. **Pricing**
   - 官方成本
   - 本站积分定价
   - markup
   - 价格更新时间

6. **Health**
   - 错误率、429、5xx、延迟
   - 自动熔断记录
   - Key 级健康历史

## 6. 模型扫描与发布流程

### 6.1 扫描原则

每天扫描供应商模型清单是合理的，但**扫描结果不能自动发布给用户**。

推荐流程：

```text
定时扫描
  -> 写入 ProviderModel(lifecycle=discovered)
  -> 对比新增/删除/价格变更/参数变更
  -> 管理员审核
  -> 测试调用
  -> 绑定 canonical model 或新建 canonical model
  -> 发布到工作台
```

### 6.2 扫描来源

不同供应商能力不同：

- OpenAI / 方舟类：模型列表 API + 文档补充
- 即梦类：文档 req_key + 手工 verified
- Tripo / 腾讯类：静态表 + 手工维护
- Kling / Runway：API 或后台配置

### 6.3 变更检测

扫描应记录：

- 新模型
- 模型下线
- 模型 deprecated
- 上下文长度变化
- 支持尺寸变化
- 价格变化
- API 参数变化

价格或参数变化应进入“待确认”，避免生产环境自动涨价或自动暴露不兼容参数。

## 7. 工作台消费方式

工作台不直接读取供应商全量模型，而读取“已发布模型目录”。

```ts
type PublishedWorkspaceModel = {
  canonicalModelId: string;
  displayName: string;
  modality: AiModality;
  description?: string;
  badges?: string[];
  parameterProfile: unknown;
  availability: {
    enabled: boolean;
    reason?: string;
  };
};
```

工作台创建任务时提交：

```ts
{
  modality: "image",
  capability: "text_to_image",
  canonicalModelId: "gpt-image-2",
  input: {...}
}
```

AI Gateway 再根据管理员策略解析 route，而不是让前端选择具体供应商 Key。

## 8. BYOK 与平台 Key 池

需要明确区分两种路径：

### 8.1 平台 Key 池

平台 Key 池由管理员维护，适用于：

- 平台代付
- 统一计费
- 套餐权益
- 自动熔断、限流和成本控制
- 多 Key 轮换

### 8.2 用户 BYOK

用户 BYOK 适用于：

- 用户自备供应商账号
- 平台不承担上游成本
- 用户侧凭据隔离
- 可作为高级用户功能

同一供应商可以同时支持平台 Key 池和 BYOK，但必须在 UI 和计费上明确区分。

例如火山方舟：

- 平台 Key 池：管理员配置方舟 API Key，平台统一调用和计费
- 用户 BYOK：用户在前端设置自己的方舟 API Key 和 Base URL

短期可以保留前端 BYOK，长期建议统一收敛进“连接账户 / 我的供应商凭据”，不要和管理员供应商中心混在一起。

## 9. 同一模型多供应商问题

### 9.1 推荐做法

使用 `canonicalModelId` + `providerModelId` 双 ID。

示例：

```text
canonicalModelId: gpt-image-2
  route 1: provider=openai, providerModelId=gpt-image-2
  route 2: provider=volcengine-ark, providerModelId=ep-xxx
  route 3: provider=toapis, providerModelId=gpt-image-2
```

用户默认看到“GPT Image 2”，管理员看到它背后的供应路径。

### 9.2 什么时候拆成不同 canonical model

如果两个供应路径虽然名字相同，但在以下方面差异很大，应拆成不同 canonical model：

- 输出质量明显不同
- 参数不兼容
- 尺寸/参考图能力不同
- 价格差异大到影响产品档位
- 合规或地域差异明显

### 9.3 工作台是否显示供应商

默认不显示供应商，降低用户认知负担。

高级模式或企业后台可显示：

- 模型名
- 供应商
- 路由状态
- 预计成本
- 延迟/稳定性

## 10. 路由策略

推荐策略顺序：

1. 过滤未启用供应商
2. 过滤未启用模型
3. 过滤当前套餐不可见模型
4. 过滤无可用 Key 的供应商
5. 过滤健康状态不可用 route
6. 按管理员优先级选择 route
7. 失败时按 fallback policy 切换

伪代码：

```ts
function pickRoute(input) {
  const routes = listRoutes(input.canonicalModelId)
    .filter(routeEnabled)
    .filter(providerEnabled)
    .filter(planVisible)
    .filter(hasHealthyKey)
    .sort(byPriority);

  return routes[0] ?? null;
}
```

## 11. 计费与成本

计费应落在 route 或 provider model 维度，而不是只落在工作台能力维度。

每次任务应记录：

- `providerId`
- `providerModelId`
- `canonicalModelId`
- `routeId`
- `billingSku`
- `estimatedCost`
- `actualCost`
- `creditsCharged`
- `settlementSource`

价格来源：

1. 官方价格扫描或手工录入
2. 管理员确认
3. 本站定价策略
4. usage event 结算

## 12. 迁移路线

### Phase 0：术语和数据模型冻结

- 新增本设计文档
- 冻结 Provider / ProviderModel / CanonicalModel / Route 概念
- 后续接入供应商按此文档命名

### Phase 1：供应商中心 UI 骨架

- 把现有 AI Key 池重命名为供应商中心
- 供应商按名称展示
- 每个供应商显示官网、控制台、文档、价格页
- 现有 Tripo、即梦、OpenAI、方舟、Vertex、ToAPIs 先以静态目录进入

### Phase 2：Key 池统一

- 将 Tripo、即梦、方舟等纳入统一 ProviderKey
- 支持不同 auth scheme
- 保留已有环境变量作为只读兜底
- 后台显示 Key 级健康状态

### Phase 3：Provider Model Catalog

- 建立供应商模型清单
- 支持静态录入和 API 扫描
- 模型默认 discovered，不自动发布
- 管理员审核后启用

### Phase 4：Canonical Model 与 Route

- 建立平台逻辑模型
- 把现有 `providerBindings` 迁移为 route
- 支持同一 canonical model 多供应路径
- 支持优先级、兜底和暂停

当前状态：已用 `canonicalModelCatalog.ts` 和 `modelRouteCatalog.ts` 做静态目录，覆盖现有文本、生图、即梦、Tripo、腾讯混元种子数据；尚未提供后台可视化编辑，也未改变现有运行时选路。

### Phase 5：工作台读取发布目录

- 工作台模型选择只读取 published catalog
- 能力入口固定为文、图、视频、3D、音乐
- 任务提交 canonicalModelId
- AI Gateway 负责 route 解析

当前状态：`publishedModelCatalog.ts` 已把已发布 canonical model 过滤为当前工作台可消费的文本/生图 registry 行；`merge.ts` 的有效文本/生图模型列表已从该发布目录读取，并继续叠加现有运营 allowlist、凭证就绪和降级逻辑。为避免行为突变，即梦仓库图模型不会进入通用对话生图选择器。

## 14. 命名规范

推荐命名：

- `providerId`: `volcengine-ark`, `volcengine-jimeng`, `openai`, `google-vertex`
- `providerModelId`: 供应商真实 model 或 endpoint id
- `canonicalModelId`: 平台逻辑模型 id
- `routeId`: `${canonicalModelId}:${providerId}:${providerModelId}`
- `billingSku`: 面向计费和价格表的稳定 SKU

避免命名：

- 不用具体模型名命名供应商 Key 池
- 不用能力名代替供应商名
- 不把 `jimeng-video-key`、`tripo3d-key` 这类名字作为长期结构

4. 价格变更是否需要审批流？
5. 企业客户是否需要自定义供应商路由？
6. 工作台高级模式是否暴露供应商路径？
7. Provider Model 和 Canonical Model 是否需要分开建表，还是 Phase 1 先用 JSON 配置承载？

---

## 16. 最小可行落地

最小可行版本不需要一次性重写所有模型中心。

建议先做：

1. `ProviderCatalog` 静态表
2. 管理员供应商中心 UI
3. ProviderKey 统一展示
4. 每个供应商附官网、控制台、文档、价格页
5. ProviderModel 静态清单
6. 管理员勾选启用模型
7. 工作台读取已启用模型

等静态版本跑通后，再接每日扫描和自动变更检测。
