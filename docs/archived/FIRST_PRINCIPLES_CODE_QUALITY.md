# 第一性原理代码质量规范

## 核心判断
代码质量不是“看起来整洁”，而是系统是否能长期、稳定、可控地交付正确结果。

每次审查都先回答 5 个问题：

1. `正确性`：正常、异常、边界输入下是否仍返回可预期结果。
2. `安全与边界`：密钥、权限、外部服务、运行环境是否放在正确边界内。
3. `可控性`：超时、重试、日志、资源释放、失败恢复是否可观测且可终止。
4. `可维护性`：模块职责、状态边界、类型契约是否清晰，是否能低风险修改。
5. `工程护栏`：是否有自动化校验来阻止同类问题再次进入主干。

## 评分规则
每个模块按 1-5 分评估：

- `5`：边界清晰，有自动化护栏，异常流完整，改动成本低。
- `4`：主体健康，存在局部缺口，但风险可控。
- `3`：功能可用，但边界或异常流不稳定，回归风险中等。
- `2`：高耦合或缺关键护栏，容易出现错误结果或难恢复失败。
- `1`：存在明显安全、正确性或资源失控风险，应优先修复。

## 审查顺序
- 先查 `会导致错误结果/泄露/服务失控` 的问题。
- 再查 `主链路状态一致性`。
- 最后处理 `结构性可维护性` 与 `工程规范补齐`。

## 必查清单
### 正确性
- 输入校验是否覆盖空值、越界、非法组合、脏数据。
- 图/任务/工作流是否能明确区分成功、失败、部分完成、不可执行。
- 多步骤流程是否会在中途失败后返回伪成功。

### 安全与边界
- 服务端密钥是否泄露到前端构建产物、浏览器存储或日志。
- 代理接口是否限制可访问目标、动作、来源与体积。
- 本地开发便利手段是否被默认带入生产路径。

### 可控性
- 请求是否有超时、终止、大小限制和错误归一化。
- WebGL、对象 URL、事件监听、轮询是否正确清理。
- 大文件、大图、大模型是否有硬护栏阻止 OOM 或长时间卡死。

### 可维护性
- 单文件是否承担过多状态与职责。
- UI 组件是否直接操纵大量副作用。
- 类型与契约是否表达真实约束，而不是靠注释和约定维持。

### 工程护栏
- 是否有 `typecheck`、`lint`、关键路径测试。
- 校验是否纳入日常脚本，而不是依赖人工记忆。

## 当前仓库首轮重点
- `vite.config.ts`：前后端边界与环境变量暴露。
- `services/settingsStore.ts`、`services/tencentService.ts`：密钥落点与调用边界。
- `server/ai3d-proxy.js`：SSRF、任意转发、响应体积与超时。
- `services/capabilityExecutor.ts`：图执行失败被伪装成成功。
- `components/UnifiedModelViewer3D.tsx`：异步竞态与资源释放。
- `WebSeamRepair/backend/main.py`、`seam_repair.py`：上传、参数与算法复杂度护栏。

## 修复原则
- 默认采用更安全的行为，危险能力必须显式开启。
- 先增加边界与校验，再做大规模重构。
- 每次改动都尽量附带脚本或测试，避免问题回流。
