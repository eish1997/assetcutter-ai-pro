# 供应商插头接入规范

目标：新增供应商时不要散改链路，而是像插插头一样补齐固定插槽。插槽不完整时，`npm run guard:provider-plug` 必须失败。

## 六个插槽

1. Provider Catalog
   - 文件：`services/modelRegistry/providerCatalog.ts`
   - 定义供应商 id、展示名、支持类型、Key 字段、能力状态。

2. Provider Model Catalog
   - 文件：`services/modelRegistry/providerModelCatalog.ts`
   - 定义供应商原始模型、registryId、模型类型、状态。

3. Canonical Model
   - 文件：`services/modelRegistry/canonicalModelCatalog.ts`
   - 定义工作台看到的统一模型 id、类型、发布状态、可见性。

4. Route
   - 文件：`services/modelRegistry/modelRouteCatalog.ts`
   - 定义 canonical model 到供应商模型的目录路由。
   - 文件：`shared/aiGatewayModelRoutes.js`
   - 定义前后端共享的 Gateway 可执行规则。

5. Worker / Adapter
   - 文件：`server/ai-gateway/provider-router.js`
   - 定义运行时 provider route。
   - 文件：`server/ai-gateway/workers/*-worker.js`
   - 定义 worker 支持的 adapter 和执行逻辑。
   - 文件：`server/ai-gateway/adapters/*`
   - 定义真实请求和产物解析。

6. Diagnostics
   - Route Check：`POST /api/admin/model-route-test`
   - Generation Test：`POST /api/admin/model-generation-test`
   - Batch Diagnostics：`POST /api/admin/model-diagnostics/run`
   - text/image 已启用可执行模型必须能被诊断链路覆盖。

## 守门命令

```powershell
npm run guard:provider-plug
```

该命令检查：

- Provider id 是否唯一。
- Provider Model 是否引用已登记供应商。
- Provider Model 类型是否被供应商支持。
- Route 是否引用已登记供应商、已登记 canonical model、已登记 provider model。
- 已启用且 `gateway_ready` 的 route 是否有共享 Gateway 可执行规则。
- 需要平台 Key 的 route，其供应商是否支持 Key 池并声明了 Key 字段。
- 已启用可执行 route 是否有运行时 provider route、active worker 和 worker 支持的 adapter。

`npm run guard:ai-routing` 已串联执行该守门命令。

## 新供应商接入顺序

1. 先补 Provider Catalog，不接任务。
2. 补 Provider Model Catalog，只展示模型，不发布。
3. 补 Canonical Model，默认 draft。
4. 补 Route 和共享 Gateway 规则，先标 pending 或 adapter_pending。
5. 补 Worker / Adapter，并把 route 切到 gateway_ready。
6. 在供应商中心录入 Key，跑 Route Check。
7. 对 text/image 跑 Generation Test 或批量 diagnostics。
8. 通过后再发布到 workspace。

原则：目录展示、发布可选、后端可执行、线上诊断必须分层推进，不要一次性跳过中间插槽。
