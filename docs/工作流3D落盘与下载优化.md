# 工作流 3D 落盘与下载 — 优化方案

**状态**：方案文档（待按里程碑落地）  
**相关代码**：`services/tripoModelPersist.ts`、`services/tencentModelPersist.ts`、`services/downloadModelFile.ts`、`services/workflowCompanionAssets.ts`、`components/WorkflowSection.tsx`、`components/preview/viewers/ImageModel3DViewer.tsx`、`server/auth-api.js`（`POST /api/tripo/fetch-file`）  
**关联错题**：`docs/错题本.md`（Tripo 本地化、fetch-file 404、另存为黑屏、blob 格式识别）

---

## 1. 背景与目标

### 1.1 用户心智

用户期望的流程：

1. 工作流生成 3D 成功后，**GLB / FBX 落到本机**（可长期保存）；
2. 在大图里预览模型；
3. 点「下载」时，**从本机已归档文件**导出到用户自选的保存位置。

### 1.2 当前实现（摘要）

```text
云端（Tripo / 混元）
    ↓ auth-api 或混元 proxy 拉二进制
本地伴侣卷（可选，putCompanionAsset）
    ↓ 读回
浏览器 blob: URL（stepModelUrls / modelUrls，供预览）
    ↓ 点下载
<a download> 另存为 → 用户指定路径
```

**关键差异**：

| 用户理解 | 当前实现 |
|----------|----------|
| 文件在「本地盘」 | 在 **本地伴侣** 管理的卷目录（非用户 Downloads） |
| 下载从磁盘读 | **优先读 blob:**，伴侣键多为后备 |
| 生成后必有 GLB+FBX | Tripo：FBX 为二次 convert，**可能失败仅留 GLB**；混元：按接口返回格式 |

### 1.3 已暴露的问题（2026-05 跨机测试）

- Vercel 静态站：`fetch-file` 曾走同源导致 404（已修：走 `VITE_AUTH_API_BASE_URL`）。
- 未连伴侣：仅内存 `blob:`，刷新后预览/下载失效。
- `blob:` URL 无扩展名 → 3D 视口格式识别失败（已部分修：`inferModelFormat` + `modelFileName` 兜底）。
- 系统「另存为」对话框弹出时 WebGL 上下文丢失 → 大图发黑（已部分修：监听 `webglcontextlost`、延后 revoke）。

### 1.4 优化目标

1. **真相源清晰**：持久化以伴侣槽位为准，blob 仅为缓存。
2. **状态可见**：用户一眼知道「已落伴侣 / 仅内存 / 归档失败」。
3. **跨设备可预期**：生成前检查伴侣与 auth-api；失败可恢复（Tripo taskId / 混元 jobId）。
4. **下载稳定**：少绕 blob，减少与 WebGL 预览的资源竞争。

**非目标**（本方案不做）：

- 浏览器直接写入用户任意文件夹（无 OS 权限）。
- 用 IndexedDB 默认存整颗 GLB 替代伴侣（体积与职责重复）。

## 2. 现状数据模型

### 2.1 资产卡字段（`WorkflowAsset`）

| 字段 | 用途 |
|------|------|
| `stepModelUrls[resultKey][]` | 按步骤的预览/下载 URL（多为 `blob:`） |
| `stepModelCompanionKeys[resultKey][]` | 伴侣存储键，槽位 0=GLB、1=FBX（Tripo） |
| `stepModelFormats[resultKey][]` | `'glb' \| 'fbx'` |
| `modelSourceName` | 下载文件名提示 |
| `resultMeta[resultKey].tripoTaskId` / `tencentJobId` | 云端任务恢复 |
| `resultMeta[resultKey].mediaKind` | `'model3d'` 等 |

### 2.2 归档入口

| 提供商 | 模块 | 行为 |
|--------|------|------|
| Tripo | `persistTripoModelsForWorkflowAsset` | GLB 必落；FBX 经 `convert_model` 尽力落槽位 1 |
| 混元 | `persistTencentModelsForWorkflowAsset` | 按 `ResultFile3Ds` 多槽落盘 |
| 回填 | `patchWorkflowAssetsWith3dResult` | 写 `stepModel*` + `resultMeta` |

### 2.3 下载入口

- 工作流大图：`WorkflowSection.handleLightboxDownloadModel` → `downloadWorkflowStepModelSlot`
- **两层逻辑**（易误读，需区分）：
  1. `downloadWorkflowStepModelSlot`：**仅当 `url` 为空** 且有 `companionKey` 时，先走伴侣读回再下载（已实现）。
  2. `resolveModelBlob`（`downloadModelFromSource` 内）：**只要 `url` 非空**（含失效的 `blob:`），一律先尝试 `url`，伴侣键为后备。

因此常见故障是：bundle 里仍留着刷新后已死的 `blob:` 字符串 → 下载走 url 分支失败，**不会**自动落到伴侣。

### 2.4 预览入口

- `ImagePreviewOverlay` + `ImageModel3DViewer`
- `modelUrls` 来自 `resolveWorkflowStepModelUrls`；`modelFileName` 来自 `modelSourceName` 或格式兜底

### 2.5 伴侣预览恢复（已有，但有缺口）

`WorkflowSection` 内 `companionModelHydrateKey` effect（约 1513 行起）：

- 对 `workflowAssetNeedsCompanionModelHydrate` 为 true 的资产，从伴侣读回并写入 `stepModelUrls` / `modelUrls`。
- **跳过条件**：槽位已有 `blob:` / `https:` / `data:` 则**不覆盖**。

缺口：刷新后 bundle 常仍带**失效** `blob:`，needs-hydrate 为 false、effect 也不替换 → **预览黑屏**，且下载仍优先死 blob。

轻量上云 `stripInlineMediaFromWorkflowBundleForLiteSync` 会把 `blob:` 剥成空串，**云对账拉下来的 bundle** 反而更容易触发伴侣恢复；**本机 IndexedDB 未同步**时问题更明显。

### 2.6 遗留字段

| 字段 | 说明 |
|------|------|
| `modelUrls[]` / `modelCompanionKeys[]` | 资产级遗留；`workflowStepModels.inferLegacyWorkflowStepModelOwnerKey` 按 `tripoTaskId` / `tencentJobId` 归属到某步骤 |
| `stepModel*` | 新路径，按 `resultKey`（如 `generate_3d`、`hunyuan_pro`）分槽 |

P1 槽位统一时需兼容合并读，避免只改 step 级漏掉老项目。

## 3. 问题根因归纳

### 3.1 架构层

- **双通道真相**：伴侣键与 blob URL 并存，但下载/预览未统一「以伴侣为准」。
- **blob 易失**：刷新、关标签、revoke、跨标签不共享。
- **静态部署依赖 auth-api**：Tripo 拉文件、上传、任务查询均需 `VITE_AUTH_API_BASE_URL`，与 Vercel 仅托管 HTML/JS 分离。

### 3.2 体验层

- 落盘成功/失败信息只在运行日志，UI 无三态展示。
- FBX 缺失时仍显示下载按钮或用户不知仅有 GLB。
- 另存为与 WebGL 同页，GPU 被系统对话框抢占。
- **失效 blob 占位**：伴侣已有归档，但 bundle 仍记 `blob:`，hydrate 与下载均不回落伴侣（见 §2.5）。

### 3.3 跨设备层

- 「其它电脑」= 浏览器所在机器；伴侣在 A 机、浏览器在 B 机时，**归档在 A、B 上无文件**。
- 未连伴侣时整条链路退化为内存，与「已下载到本地盘」预期不符。
- 轻量上云会保留 `stepModelCompanionKeys`、剥离 `blob:`；B 机 bundle 有键无字节，需连 **A 机伴侣** 或 Tripo/混元重拉，否则预览/下载皆空。

### 3.4 恢复能力不对称

| 提供商 | 任务 id 持久化 | UI「从云端拉取」 | 模块 |
|--------|----------------|------------------|------|
| Tripo | `tripoTaskId` | 有（「从 Tripo 拉取」） | `workflowTripoModelRehydrate.ts` |
| 混元 | `tencentJobId` | **无**（时间线仅展示/复制 JobId） | 待补 `workflowTencentModelRehydrate.ts` 或复用门面 |

文档 §6 第 3 条写「混元 jobId 可恢复」为**目标态**，非当前全链路能力。

## 4. 优化原则

1. **字节真相在本地伴侣**（与 `docs/本地与云存储分层开发方案.md` 第一性原理一致）：可恢复的二进制以伴侣卷 + `companionKey` 为准。
2. **blob 是缓存，不是契约**：可重建：`companionKey` → `fetchCompanionAssetBlob` → 临时 object URL。
3. **槽位元数据驱动 UI**：`stepModelFormats` + `companionKey` 决定预览格式、下载按钮显隐、文件名。
4. **失败可恢复**：持久化 `tripoTaskId` / `tencentJobId`；UI 提供「继续查旧任务 / 从 Tripo 拉取」。
5. **渐进落地**：P0 改优先级与 UI；P1 改传输方式；P2 抽象与策略，避免大爆炸重构。

## 5. 方案详述

### 5.1 P0 — 伴侣优先下载 + 落盘状态 UI

#### 5.1.1 下载：`resolveModelBlob` 调整优先级

**现状**（简化，见 §2.3）：

```text
downloadWorkflowStepModelSlot:
  if (!url && companionKey) { 伴侣 → 再 download }   // 已有
  else → downloadModelFromSource → resolveModelBlob:
    if (url) { blob / https … }   // 含失效 blob
    else if (companionKey) { 伴侣 }
```

**目标**：

```text
if (companionKey && companionReachable) { 伴侣 }
else if (url && urlStillReadable) { blob / https / fetch-file }
else if (companionKey) { 伴侣 }  // 离线后再试一次
else { 报错 + 引导拉取 }
```

**`companionReachable`**：尚无统一 `isCompanionOnline()`，可复用 `getCompanionLocalBaseUrl()` + 现有健康检查或 `GET /v1/projects` 轻量探测（实现时抽到 `companionClient`）。

**涉及**：`services/downloadModelFile.ts`  
**验收**：刷新后 blob 失效，伴侣在线时仍可下载 GLB/FBX。

#### 5.1.1b 失效 blob 清理与预览恢复（建议与 5.1.1 同迭代）

与「下载伴侣优先」配套，否则 P0 只改下载仍可能预览黑屏。

1. **`workflowAssetNeedsCompanionModelHydrate`**：对 `blob:` 槽位增加探测（`fetch(blobUrl)` 失败 → 视为需 hydrate）；或打开大图时对当前槽位做一次探测。
2. **hydrate effect**：探测失败时 `revoke` 旧 blob、清空槽位，再从伴侣读回。
3. **可选**：项目 load 完成后批量 `healStaleWorkflowModelBlobSlots(assets)` 写回 bundle。

**涉及**：`services/workflowCompanionAssets.ts`、`components/WorkflowSection.tsx`  
**验收**：本机 IndexedDB 含死 blob + 有效 `companionKey`，打开项目后 3D 预览自动恢复，无需手点「从 Tripo 拉取」。

#### 5.1.2 UI：落盘三态徽章

在大图 3D 工具条（`WorkflowSection` `lightboxShowTripo3DToolbar` 区域）或步骤时间线详情展示：

| 状态 | 条件 | 文案示例 |
|------|------|----------|
| `persisted` | 对应槽位有 `companionKey` | 已落本机伴侣 · GLB ✓ FBX ✓/— |
| `memory_only` | 仅有 `blob:`、无伴侣键 | 仅浏览器缓存，刷新可能丢失 |
| `failed` | 有 taskId 但无模型槽位 | 归档失败 · 可「从 Tripo 拉取」 |
| `remote_only` | 有 `tencentJobId` / `tripoTaskId`，无本地槽位 | 仅云端任务 · Tripo 可拉取；混元待补按钮 |

数据来源：`resolveWorkflowStepModelUrls` + `stepModelCompanionKeys` + `getCompanionLocalBaseUrl()`。

**展示位置建议**：大图 3D 工具条（主）+ 时间线详情（辅）；资产卡缩略图不必首版做。

#### 5.1.3 生成前轻量检查（可选同迭代）

执行 `generate_3d` 前：

- `VITE_AUTH_API_BASE_URL` 可达（或同源 `/api/tripo` 在 dev）；
- 伴侣已连接且 `activeWorkspaceProjectId` 有效。

不满足：**警告条**（不阻断或产品决定阻断），避免用户以为「已落盘」。

### 5.2 P1 — 伴侣直传下载 + 槽位元数据统一

#### 5.2.1 伴侣 `attachment` 下载

避免：`伴侣 → 内存 blob → createObjectURL → download → revoke`。

建议：伴侣 API 支持（或复用现有 GET）：

```http
GET /v1/projects/{pid}/assets/{key}?download=1
Content-Disposition: attachment; filename="xxx.glb"
```

前端下载改为 `window.location` / 隐藏 iframe / `fetch` + `download`，**不经过预览用 blob**。

**涉及**：`local-companion`、`services/companionClient/storage.ts`、`downloadModelFile.ts`。

#### 5.2.2 槽位元数据单源

约定每个槽位结构（可逐步类型化）：

```ts
type WorkflowModelSlot = {
  format: 'glb' | 'fbx';
  companionKey?: string;
  previewBlobUrl?: string; // 可选缓存，可失效
  sourceName?: string;
};
```

预览、下载、时间线导出**只读** `stepModelSlots[resultKey]`，不再从 URL 猜扩展名。

**涉及**：`types.ts`（可选扩展）、`workflowStepModels.ts`、`patchWorkflowAssetsWith3dResult`。

#### 5.2.3 预览与下载解耦

- 预览：仍可 `blob:` 或伴侣读回 object URL（性能）。
- 下载：**禁止**与预览共用同一 object URL 的 revoke 时机；下载走独立 fetch 或 attachment。

### 5.3 P2 — 提供商策略与代码收敛

#### 5.3.1 Tripo vs 混元 FBX 策略

| 提供商 | GLB | FBX | UI |
|--------|-----|-----|-----|
| Tripo | 必归档 | convert 尽力；失败仅 GLB | FBX 按钮无槽位则禁用 + tooltip |
| 混元 | 按预设 | 有则落盘，无则不转 | 按 `stepModelFormats` 显示 |

可选：Tripo FBX convert 失败后后台重试一次（不阻塞 GLB 回填）。

#### 5.3.2 统一归档门面

```ts
persistWorkflow3dSlots({
  provider: 'tripo' | 'tencent',
  taskId,
  filesOrUrls,
  companion: { base, projectId },
  assetId,
  resultKey,
  options: { includeFbxArchive?: boolean },
})
```

内部调用现有 `tripoModelPersist` / `tencentModelPersist`，减少一边修另一边漏。

#### 5.3.3 独立「生成3D」页

已移除独立页；3D 仅工作流 + 能力预设。`useGenerate3DManager` 可保留给测试或后续删除，**拣货索引** `workflowAiPickIndex` 的 `codeRefs` 应改为 `App.tsx` + `services/generate3d/`。

## 6. 跨设备与部署说明（产品文案用）

写入设置/帮助或生成前警告：

1. **本地伴侣**跑在哪台机器，**3D 文件就落在哪台**的伴侣卷里。
2. **Vercel 前端**只跑界面；Tripo 拉文件、上传必须配置 **`VITE_AUTH_API_BASE_URL`** 指向 auth-api（如 Render）。
3. 未连伴侣时：模型仅在**当前浏览器标签**内存中，**刷新丢失**；可凭 `tripoTaskId` 经「从 Tripo 拉取」恢复；混元 `jobId` 目前仅便于人工/query，**尚无对等一键恢复**（见 §3.4）。

## 9. 手测清单

### 9.1 本地开发（伴侣 + auth-api）

1. 工作流 Tripo 图生 3D → 日志「落盘 GLB」→ UI **已落伴侣**。
2. 大图切 **3D 模型** → 可旋转预览。
3. **刷新页面**（不关伴侣）→ 预览应自动恢复（M1 后）；下载 GLB 仍成功。
4. 点下载 → 另存为 → 文件可本地打开；大图**不应长期黑屏**（若黑，关对话框后重开大图）。
5. **死 blob 专项**：生成后 F5，确认 bundle 内仍有 `blob:` 字符串时，hydrate 能替换并成功预览。

### 9.2 Vercel + Render auth-api

1. 构建含 `VITE_AUTH_API_BASE_URL`。
2. Network：`fetch-file` 请求 host 为 **auth-api 域名**，非 vercel.app。
3. 生成成功并完成落盘（伴侣需在可访问机器上）。

### 9.3 无伴侣

1. 生成成功 → UI **仅浏览器缓存**。
2. 刷新 → 预览丢失；有 taskId 时「从 Tripo 拉取」可恢复。

## 10. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 伴侣优先导致离线 blob 也不能下 | 保留 blob 后备路径 |
| attachment 跨域 Cookie | 与现有伴侣鉴权一致，必要时同源代理 |

## 12. 评审补充（问题、建议、待决）

### 12.1 原文档需修正或细化的点

| 项 | 说明 |
|----|------|
| 下载优先级表述过粗 | 并非全程 url 优先：`url` 为空时 `downloadWorkflowStepModelSlot` 已伴侣优先（§2.3） |
| 刷新后「能下载不能预览」 | 根因常是**失效 blob 占位**阻止 hydrate，不单是 `resolveModelBlob` 顺序 |
| 混元恢复 | 勿写成已具备一键恢复；当前仅 Tripo 有 `rehydrateWorkflowAssetModelsFromTripoTask` |
| `companionOnline` | 代码中尚无统一探测，实现 P0 时需新增约定 |

### 12.2 建议上调优先级

1. **P0 捆绑「失效 blob 自愈」**（§5.1.1b）— 与下载伴侣优先同等重要，否则手测仍会出现「刷新后 3D 黑屏」。
2. **下载避免双重读伴侣** — `downloadWorkflowStepModelSlot` 在 `!url` 分支先 `fetchWorkflowModelFromCompanionAsObjectUrl` 再 `downloadModelFromSource`，大 GLB 占双倍内存与时间；伴侣优先后应直传 blob 或 attachment，不再绕一圈 objectUrl。
3. **混元 rehydrate（P1）** — 与 Tripo 对称，否则时间线 JobId 仅作展示。

### 12.3 产品待决（实现前建议拍板）

| 决策 | 选项 |
|------|------|
| 未连伴侣是否允许生成 3D | A. 仅警告（现状） B. 阻断并引导开伴侣 |
| 跨机使用默认预期 | A. 必须连「归档所在那台」伴侣 B. 接受仅云端 taskId + 重拉 |
| FBX 失败是否阻塞「生成成功」 | 现状：不阻塞；是否在 UI 标「部分成功」 |
| 生成成功后是否清空旧 blob 槽位 | 建议：落伴侣成功后写 companionKey 并**去掉**可失效 blob，减少 heal 成本 |

### 12.4 与现有能力对齐（不必重复造轮）

- **轻量上云**已剥 blob、留 `stepModelCompanionKeys` — 跨标签/跨机靠键 + 伴侣，文档策略一致。
- **`mergeLiteStructurePreservingCloudObjectKeys`** 会合并云端 companion 键 — 实现 heal 时注意勿在 merge 时写回死 blob。
- **`manifest/reconcile`**：伴侣磁盘有文件但 manifest 缺条时，拉取前可先 reconcile（见 `docs/本地伴侣-存储与计算规范.md`）。
- **错题本已记** fetch-file 404、WebGL 丢失 — P0 落地后把「死 blob 占位」补一条，便于检索。

### 12.5 非目标可再明确一条

- **不把 `stepModelUrls` 里的 blob 持久化进 IndexedDB 作为长期方案** — 当前会写入；长期应倾向「仅存 companionKey + 运行时 objectUrl」，bundle 体积与刷新一致性更好（可与 P1 槽位元数据一并做）。
