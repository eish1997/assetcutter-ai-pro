# 供应商模型发布闭环审计

**日期**：2026-07-15
**状态**：审计结论与后续优化建议
**目标**：确认“后台接 Key、勾选发布模型、前端工作台可选择并成功执行”的完整闭环是否成立。

## 1. 结论

当前系统已经具备供应商目录、模型清单、Key 池、发布清单、Gateway 路由守卫和部分执行 adapter，但还没有完全收成一个产品化闭环。

最核心的问题是：**后台展示和发布能力已经走在运行时能力前面**。管理员能看到更多供应商模型，也能把部分模型加入发布清单，但前端是否显示、Gateway 是否放行、Key 是否真实可用、adapter 是否能完成任务，仍由多套逻辑分别判断。

因此现在不能简单理解为“勾选发布 = 前端可用”。更准确的状态是：

```text
供应商模型目录存在
  -> 可能进入发布清单
  -> 前端可能显示
  -> Gateway 创建任务时再做 route/key 拦截
  -> adapter 存在时才会真实执行
```

期望的产品状态应该改成：

```text
供应商 Key 可用
  + 模型 route 可执行
  + 参数/输出映射已完成
  + 管理员发布
  -> 前端工作台显示
  -> 用户提交任务
  -> Gateway 执行并产出统一资产
```

## 2. 当前闭环拆解

| 环节 | 当前状态 | 主要问题 |
|---|---|---|
| 供应商目录 | 已有 `providerCatalog` | 状态矩阵能表达“待后端/可配 Key”，但还没有成为发布硬门槛 |
| 模型目录 | 已有 provider model / canonical model / route catalog | canonical 发布状态、Gateway 可执行状态、前端旧 registry 过滤没有完全统一 |
| Key 池 | 支持多供应商保存 Key | 除 Tripo 外多数供应商仍是凭证字段检查，不是真实任务探活 |
| 发布清单 | `publishedCanonicalModelAllowlist` 已落盘 | 只代表“运营允许”，不代表“运行时可用” |
| 后端守卫 | `/api/ai/jobs` 已接发布校验和 route/key 校验 | 发布校验本身不校验 gateway_ready；实际执行入口才拦截 |
| 前端选择 | 部分入口已读 effective model rows | 文本/图片仍受旧 registry 限制；视频/3D入口还需要继续统一 |
| 执行 adapter | Gemini、OpenAI-compatible、即梦视频、Tripo P1 已有路径 | 方舟、腾讯混元、Tripo 其它模型等仍未完整可执行 |

## 3. 关键发现

### 3.1 发布清单不是可执行清单

`server/ai-gateway/model-publication-guard.js` 只检查请求模型是否在 `publishedCanonicalModelAllowlist` 中，不检查该模型是否 `gateway_ready`，也不检查 Key 或 adapter。

这本身不是 bug，但产品语义需要明确：发布清单是“允许进入工作台”的运营开关，不是“可执行证明”。如果前端直接按发布清单展示，就会出现用户看到模型但任务提交后被 Gateway 拦截的情况。

建议后续把前端默认展示口径改为：

```text
published + gateway_ready + key_ready
```

高级管理模式可以显示 `Gateway 待接`、`待后端`、`缺 Key`，但普通工作台不应把这些当成可选模型。

### 3.2 前端展示仍被旧模型注册表过滤

`services/modelRegistry/publishedModelCatalog.ts` 中：

- 文本模型必须存在于 `TEXT_MODEL_REGISTRY`。
- 图片模型必须存在于 `DIALOG_IMAGE_REGISTRY`。
- 这会导致供应商模型清单里新增的方舟 `doubao-*`、`seedream-*` 等，即使被加入发布清单，也不一定能在前端模型选择器出现。

这解释了“后台多了一些支持的模型，勾选发布后前端还是不显示”的现象。

建议把前端选择器的最终来源统一成 canonical model + route readiness，而不是旧 text/image registry。旧 registry 只作为兼容字段或默认参数来源。

### 3.3 Gateway 可执行路由比供应商清单窄

`shared/aiGatewayModelRoutes.js` 当前可执行规则主要覆盖：

- Gemini / Vertex：文本、图片
- OpenAI 官方：文本、图片
- ToAPIs OpenAI-compatible：文本、图片
- 即梦：视频
- Tripo：`tripo-p1`、`tripo-v3.1`、`tripo-v3.0`、`tripo-v2.5`、`tripo-v2.0`

当前明确待接：

- 火山方舟：`doubao-*`、`seedream-*`、`seedance-*`、`seed3d-*`
- 腾讯混元 3D

明显不一致点：

- Tripo 供应商模型清单、canonical model、Gateway route 需要保持一一对齐，执行时按 registry id 映射到上游 `model_version`。
- 方舟模型已进入目录和发布清单，但仍是 `adapter_pending`。
- 腾讯混元 3D 是 published canonical model，但 Gateway 仍待接。

### 3.4 Key 测试还不是模型任务测试

`server/ai-gateway/provider-key-store.js` 中：

- Tripo 支持真实上游探活，默认请求 `GET /user/balance`。
- 其它供应商多数只检查凭证字段是否完整。

这意味着 Key 测试通过不等于模型可执行，Key 测试失败也未必等于所有任务接口都失败。比如 Tripo 的真实任务链路还会用到：

- 创建任务
- 图片上传或 STS
- 任务轮询
- 模型文件下载

建议把测试分层：

| 测试层级 | 用途 |
|---|---|
| Key 连接测试 | 验证凭证是否能访问供应商基础接口 |
| Model 测试 | 验证指定 provider model 是否存在且可调用 |
| Route 测试 | 验证 canonical model + provider route 是否能完整执行 |
| Artifact 测试 | 验证输出能转换为平台统一资产 |

### 3.5 输入/输出模态需要按 route 管理

用户提到“有些供应商的输出和输入不一致”，这个判断是对的。供应商支持某个模型，不代表它在我们的工作台固定生成类型里天然匹配。

建议 route 级别维护：

- `inputModalities`
- `outputModalities`
- `capabilities`
- `parameterSchema`
- `artifactSchema`
- `supportedWorkflows`
- `limits`

例如同样是图片模型，可能分为：

- 文生图
- 图生图
- 多图参考
- 局部编辑
- 角色一致性

如果只用 `modality: image` 表达，会不够。

## 5. 需要补齐的产品闭环

### 5.1 统一“可发布”和“可用”口径

建议新增或收敛一个统一状态：

```text
workspaceSelectable = published && gatewayReady && providerReady && keyReady && parameterReady
```

其中：

- `published`：管理员勾选发布。
- `gatewayReady`：共享 route 规则判断可执行。
- `providerReady`：供应商 adapter 和 worker 已接。
- `keyReady`：平台 Key 可用，或该 route 不需要平台 Key。
- `parameterReady`：该工作台入口所需参数可以映射。

普通用户只看 `workspaceSelectable=true` 的模型。

### 5.2 前端所有入口统一读模型源

需要统一的入口包括：

- 全局输入框 / 工作台模型选择
- 预设编辑
- 组覆盖
- 快捷生成参数面板
- 视频生成参数
- 3D生成参数
- 后续音乐、文本工具

这些入口不要再各自硬编码模型列表。它们应该按固定生成类型读取：

```text
text / image / video / model3d / music
```

然后由统一模型服务返回可用模型、默认模型、禁用原因和参数 schema。

### 5.3 管理端发布前给出阻断提示

管理员勾选模型时，UI 应该明确显示：

- 可发布且可执行
- 可发布但缺 Key
- 可发布但 Gateway 待接
- 可发布但参数未映射
- 不建议发布或只能高级预览

如果允许勾选待接模型，也应明确告诉管理员：它不会出现在普通工作台，或出现为灰态。

### 5.4 Gateway route 与 provider route 收敛

当前 `provider-router.js` 负责 provider/worker/adapter，`shared/aiGatewayModelRoutes.js` 负责模型是否可执行。两者需要继续收敛，避免一个说能走、另一个没有 route。

建议 route 统一字段至少包含：

- canonical model id
- provider id
- provider model id
- modality
- capabilities
- adapter id
- worker id
- execution status
- key requirement
- parameter mapping ref
- artifact mapping ref

### 5.5 Smoke Test 升级成 Route Test

建议保留 Key 级测试，同时新增 route 级测试按钮：

```text
测试 Key
测试模型
测试 Route
测试完整生成
```

低成本模型优先真实跑；高成本视频/3D可以先做轻量接口测试或 dry-run，但 UI 必须标清楚“这不是完整生成测试”。

## 6. 建议分轮执行

### 第 1 轮：先修“显示误导”

目标：前端普通工作台不显示不可执行模型。

- 前端统一过滤 `published + gateway_ready`。
- 管理端保留待接模型显示，但加禁用原因。
- 方舟待接部分、腾讯混元等不再误导为可用；Tripo 全量 3D 模型需按同一套清单与 route 校验。

### 第 2 轮：统一模型选择入口

目标：预设、组覆盖、全局输入框、工作台参数面板都读同一个模型选择服务。

- 移除 text/image 旧 registry 对新供应商模型的硬过滤。
- 保留旧 registry 作为兼容映射。
- 每个生成类型输出统一模型行结构。

### 第 3 轮：补 route 级可执行检查和管理端提示

目标：管理员勾选时能知道模型为什么不可上架。

- 管理端展示 `可执行 / 缺 Key / Gateway 待接 / 参数待映射`。
- 发布保存时可以保留勾选，但普通工作台只显示可用项。
- 后端提供可用性摘要接口，避免前端自己拼。

### 第 4 轮：优先收敛已接供应商

目标：先把已接近可用的供应商做到“接 Key 就能发布”。

优先顺序：

1. OpenAI 官方文本/图片
2. ToAPIs OpenAI-compatible 文本/图片
3. 即梦视频
4. Tripo 3D 全量模型（`tripo-p1`、`tripo-v3.1`、`tripo-v3.0`、`tripo-v2.5`、`tripo-v2.0`）

验收标准：接 Key、测试通过、勾选发布、前端显示、真实任务成功、资产落库。

### 第 5 轮：补方舟与其它待接供应商

目标：按供应商逐个接 adapter，不再只补目录。

火山方舟需要拆成：

- 方舟文本
- 方舟图片
- 方舟视频
- 方舟 3D

每类分别确认 endpoint、参数、输出、计费、错误码和资产类型。

## 7. 验收标准

一个供应商模型只有同时满足以下条件，才算“平台可用”：

- 管理端供应商链接、文档、控制台地址完整。
- Key 池能保存并分配该供应商 Key。
- Key 或 route 测试有明确结果。
- canonical model、provider model、route 三者能互相追踪。
- Gateway route 显示 `gateway_ready`。
- adapter 能真实执行任务。
- 输出能转成统一资产。
- 前端对应生成类型能显示并选择该模型。
- 预设、组覆盖、输入框参数能选择该模型。
- 失败时能显示可读错误，而不是笼统“请求失败”。
- 有最小单测覆盖 route guard、adapter request、任务成功/失败路径。

## 8. 下一步建议

建议下一轮先做第 1 轮和第 2 轮，先把“用户看见的模型”和“后台真正可执行的模型”对齐。这样可以立刻减少误导和测试噪音。

随后再按供应商补 adapter。否则继续先加供应商目录，会让后台看起来越来越完整，但前端和执行链路更难判断到底哪里断了。

## 10. 第 3 + 第 4 轮进展

**时间**：2026-07-15

本轮补上了管理端“发布前可用性摘要”，并将第一批已接供应商按同一套 `route + key` 口径收敛。管理员在供应商中心勾选发布模型时，现在能看到每个 canonical model 的状态：`可发布`、`缺 Key`、`参数待映射`、`Gateway 待接`、`无路由`。

已完成：

- 新增后端摘要模块 `server/ai-gateway/model-availability-summary.js`。
- 新增管理员接口 `POST /api/admin/model-availability-summary`。
- 摘要判断覆盖：
  - `ready`：有 Gateway 可执行 route，且不需要平台 Key 或已有可用平台 Key。

  - `parameter_pending`：参数或 endpoint 映射待补齐。

- 供应商中心 Workspace model publishing 卡片显示可用性徽标和不可用原因。
- 保存发布清单前会阻断不可用模型，避免“后台勾选成功但前端不可用”。

- 第一批已接供应商的判断口径收敛到同一套摘要：
  - OpenAI 官方文本/图片：有 `openai-official` 平台 Key 后可发布。
