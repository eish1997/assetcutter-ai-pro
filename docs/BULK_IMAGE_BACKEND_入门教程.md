# 批量出图后端 — 入门操作教程

面向「已部署前端网站、不熟悉后端」的同事：**后端是什么、要不要用、怎么用**，按步骤说明。

---

## 一、先搞清两件事

### 1. 前端网站现在能直接用批量出图吗？

**能。** 前端已经部署好的话，不配置后端也可以：

- 打开网站 → 对话页 → 「批量出图」照常用。
- 此时是 **纯前端模式**：  
  - 每台电脑/每个浏览器 **各自** 算「今日用了多少次」、**各自** 排队（例如本机同时最多 2 个任务）。  
  - 关掉页面或刷新，任务列表会清空（不持久化）。

所以：**不搞后端，网站上的批量出图也能用**，只是「全公司共用一个 900 次/天、全公司同时 2 个任务」做不到。

---

### 2. 什么时候需要后端？

需要下面这些时，才必须把 **批量出图后端** 跑起来并让前端连上它：

- **全公司共用一个额度**：不管谁在哪台电脑用，都算在「公司今日 900 次」里。
- **全公司同时最多 2 个任务**：多人一起点「批量生成」时，真正在跑的只有 2 个，其他排队。
- **任务持久化**：刷新页面、关掉再打开，还能看到之前的任务列表和进度。

总结：  
- 只想自己/小范围用、不关心「全公司统一限额」→ **可以不用后端**，保持现状即可。  
- 要「全公司 900 + 全公司同时 2 + 任务不丢」→ **必须部署后端**，并按下面步骤做。

---

## 二、不用后端时（保持现状）

- 前端已经部署好了，**不需要改任何配置**。
- 不要设置 `VITE_BULK_IMAGE_API`（或部署/构建时不要带这个环境变量）。
- 这样网站会一直用「纯前端模式」，每台设备各自计数、各自排队。

**无需其它操作。**

---

## 三、要用后端时：整体思路

后端就是一个 **一直运行的小程序**（Node 写的），做三件事：

1. **接收前端的「创建任务 / 查进度 / 取消」**（通过 HTTP 接口）。
2. **自己调 Google 的 Gemini 接口去生图**（用你配置的公司 Key，或前端传来的 Key）。
3. **管好两件事**：全公司「今日最多 900 次请求」+ 「同时最多 2 个请求在跑」。

所以你要做的只有两步：

1. **把这段小程序跑在一台「一直开机、大家能访问到」的机器上**（本机 / 公司服务器 / 云服务都可以）。  
2. **让前端知道这个程序的地址**（在构建或部署时设置 `VITE_BULK_IMAGE_API=你的后端地址`）。

下面按「先在自己电脑上跑通 → 再放到服务器/云上」的顺序写。

---

## 四、第一步：在自己电脑上跑通后端（本地测试）

目的：确认后端能正常启动、能连 Gemini、前端能连上它。

### 4.1 准备环境

- 本机已安装 **Node.js**（建议 18 或以上）。  
  - 未安装：到 [https://nodejs.org](https://nodejs.org) 下载安装。  
- 有项目代码（能打开 `server/bulk-image-api.js` 这个文件）。

### 4.2 配置公司用的 Gemini Key（仅后端用）

1. 在项目根目录找到 `.env.example`，复制一份，改名为 **`.env.local`**（没有就新建）。
2. 在 `.env.local` 里写上（其它可先不改）：

```bash
# 公司统一用的 Gemini API Key（后端用；前端没填 Key 时会用这个）
GEMINI_API_KEY=你的Gemini密钥
```

把 `你的Gemini密钥` 换成你在 Google AI Studio 里拿到的 API Key。  
**注意**：这个文件不要提交到 Git，不要发给别人。

### 4.3 启动后端

在项目根目录打开终端（命令行），执行：

```bash
npm run dev:bulk-api
```

或：

```bash
node --env-file=.env.local server/bulk-image-api.js
```

看到类似下面就说明启动成功：

```text
[bulk-image-api] http://127.0.0.1:9002 (RPD limit: 900, concurrent: 2)
```

说明：后端在本机 **9002** 端口运行；RPD 900、同时 2 个任务已生效。

### 4.4 让本地前端连上这个后端

1. 在 `.env.local` 里再加一行（或确认已有）：

```bash
VITE_BULK_IMAGE_API=http://localhost:9002
```

2. **重新启动前端**（例如 `npm run dev`）。  
3. 打开浏览器访问本地前端（如 http://localhost:3000），进对话页 → 批量出图，创建一个小任务（例如生成 2 张）。  
4. 若任务能创建、进度会更新，说明「前端 → 本地后端 → Gemini」这条链已通。

到这里：**后端逻辑在你本机已经跑通了**。下一步是把它放到「大家都能访问」的地方。

---

## 五、第二步：把后端部署到「大家能访问」的服务器

后端必须 **24 小时在跑**，且有一个 **对外的网址**（例如 `https://your-api.example.com`），前端才能在公司里所有人都用到「全公司 900 + 同时 2」。

可以选下面几种方式之一（任选一种即可）。

### 方式 A：公司有一台长期开着的电脑/服务器

- 在这台机器上安装 Node.js，把项目代码拷过去（或 Git 拉取）。
- 在同一台机器上建一个 `.env.local`，填好 `GEMINI_API_KEY`（以及可选 `BULK_IMAGE_DATA_DIR` 做持久化）。
- 在这台机器上运行：  
  `node --env-file=.env.local server/bulk-image-api.js`  
  并保证进程常驻（可用 `pm2`、systemd、或屏幕常开）。
- 让这台机器的 **9002 端口** 能被公司内网访问（或通过 Nginx 反代到 80/443）。
- 记下访问地址，例如：`http://公司服务器IP:9002` 或 `https://api.公司域名.com`。

### 方式 B：用云服务跑 Node（零运维感）

适合没有自己的服务器、希望「注册账号就能用」的情况。常见选择：

- **Render**（[`render.com`](https://render.com)）：新建 **Web Service**，选 Node，把整个仓库连上去。  
  - **Start command**：`node server/bulk-image-api.js`  
  - **环境变量示例**（只在 Render 上配）：  

    ```bash
    GEMINI_API_KEY=你的Gemini密钥
    BULK_IMAGE_PORT=$PORT
    BULK_IMAGE_BIND_HOST=0.0.0.0
    BULK_IMAGE_RPD_DAILY_LIMIT=900
    BULK_IMAGE_MAX_CONCURRENT=2
    # 可选：持久化目录
    # BULK_IMAGE_DATA_DIR=/data/bulk-image
    ```

  - 部署成功后会得到一个类似 `https://your-bulk-api.onrender.com` 的地址，前端就填这个。  
  - Render 会按 `$PORT` 分配端口，我们通过 `BULK_IMAGE_PORT=$PORT` + `BULK_IMAGE_BIND_HOST=0.0.0.0` 让服务在云环境上对外可见。

- 其它云服务（如 Railway、Fly.io）也类似：保证启动命令是 `node server/bulk-image-api.js`，环境变量里有 `GEMINI_API_KEY`，并监听它们提供的端口和 host。

**注意**：  
- **Gemini Key 只放在后端云服务（如 Render）的环境变量里**，不要写进前端代码或公开仓库。  
- Vercel 等前端平台不再需要任何 `GEMINI_*` 环境变量，只需要一个 `VITE_BULK_IMAGE_API` 指向后端地址。

### 方式 C：和前端同一台服务器（同一域名不同路径）

若前端是 Nginx 反代到 Node/静态资源，可以在同一台机再起一个 Node 进程跑 `server/bulk-image-api.js`，在 Nginx 里加一条反向代理，例如：

- 前端：`https://你的网站.com`  
- 后端：`https://你的网站.com/api/bulk-image` → 反代到本机 9002。

这样前端里 `VITE_BULK_IMAGE_API` 就填 `https://你的网站.com/api/bulk-image`（注意不要末尾多写 `/jobs`，前端会自动拼路径）。

---

## 六、第三步：让已部署的前端连上这个后端

前端是 **构建时** 把「后端地址」写进去的，所以：

1. **拿到后端的公网（或公司内网）地址**  
   - 例如：`https://your-bulk-api.onrender.com` 或 `http://192.168.1.100:9002`。

2. **在「构建 / 部署前端」的地方配置环境变量**  
   - 变量名：`VITE_BULK_IMAGE_API`  
   - 值：上一步的后端地址（不要末尾加 `/jobs`），例如：  
     `VITE_BULK_IMAGE_API=https://your-bulk-api.onrender.com`

3. **重新构建并部署前端**  
   - 用 Vite 的话，会执行一次 `npm run build`，这次构建会读到 `VITE_BULK_IMAGE_API` 并写进前端代码。  
   - 部署到 Vercel / Netlify / 自有服务器等，按各自方式配置该环境变量后再构建。

4. **验证**  
   - 打开已部署的网站 → 对话页 → 批量出图，创建一个任务。  
   - 若任务能创建、进度会更新，且多开几个浏览器/电脑能看到「全公司共享 900、同时 2」的效果，说明前后端都对了。

---

## 七、可选：任务和 RPD 持久化（重启不丢）

若希望 **后端重启后** 任务列表和「今日已用次数」还在：

1. 在运行后端的机器上，选一个目录专门存数据，例如 `/data/bulk-image` 或项目下的 `.data/bulk-image`。
2. 在后端的环境变量里加上（示例）：  
   `BULK_IMAGE_DATA_DIR=/data/bulk-image`  
   （Windows 可写 `BULK_IMAGE_DATA_DIR=.\.data\bulk-image`）
3. 重启后端。之后它会在这个目录下写 `jobs.json`、`rpd.json`，下次启动会自动读回来。

不设置 `BULK_IMAGE_DATA_DIR` 也可以跑，只是重启后任务列表和今日计数会清空。

## 八、常见问题简答

- **前端已经部署了，不配置后端会怎样？**  
  批量出图照常用，只是每台设备各自计数、各自排队，关页任务就没了。

- **后端必须和前端同一台服务器吗？**  
  不必。只要前端能通过 HTTP/HTTPS 访问后端地址即可（注意跨域已在后端配好）。

- **GEMINI_API_KEY 放哪里？**  
  只放在 **运行后端的机器** 的环境变量或 `.env.local` 里，不要写进前端代码或提交到 Git。

- **公司 30 人，后端放哪合适？**  
  任选：公司内网一台长期开机的电脑 + 内网地址；或 Railway/Render/Fly 等云服务，得到一个公网 URL 给前端用。

## 九、小结：你的下一步可以是什么

| 你的目标 | 建议操作 |
|---------|----------|
| 暂时不用「全公司统一 900」 | 不用动，前端已部署即可用（纯前端模式）。 |
| 要全公司 900 + 同时 2 + 持久化 | 按 **四 → 五 → 六** 步：本机跑通后端 → 把后端部署到服务器/云 → 前端构建时设 `VITE_BULK_IMAGE_API` 并重新部署。 |
