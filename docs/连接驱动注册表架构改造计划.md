# 连接驱动注册表架构改造计划

状态：可循环执行
目标读者：AI Agent、Local Companion 开发者、连接能力维护者
配套状态文档：`docs/连接改造执行状态.md`

## 1. 核心目标

把软件连接的安装、启动、探测、卸载、修复能力，从 `capabilityLifecycle.ts` 的具体软件分支中抽离出来，改造成可注册、可匹配、可验证的 `softwareBridgeRegistry + SoftwareBridgeDriver` 架构。

一句话目标：

> 后续新增一个软件连接时，只允许新增或注册一个 bridge driver，不允许再修改统一生命周期主流程。

这个目标服务于更大的产品方向：用户通过对话创建长期可执行的连接，Copilot 围绕连接对象持续安装、启动、探测、读日志、修复，而不是每遇到一个新软件都让工程师补一段硬编码。

## 2. 非目标

1. 不恢复旧的 62 个宿主中心作为产品入口。
2. 不把文件存在、安装记录、卡片存在当作 `connected`。
3. 不让 Copilot 获得任意 shell、任意写路径、任意杀进程权限。
4. 不把未真实验收的软件 driver 发布为云端正式可用版本。
5. 不在本计划中重建 workflow 产品面；workflow 迁移继续以 ScriptHub 为准。

## 3. 当前判断

当前问题不是 Maya 或 Unreal 两个连接个例，而是架构边界不够通用：

- `capabilityLifecycle.ts` 不应该知道 Photoshop、Blender、Maya、Unreal 的具体实现。
- 连接页面不应该复制一份软件识别逻辑。
- Copilot 不应该建议“改生命周期主流程”来支持新软件。
- 新软件应该通过 driver registry 成为能力，而不是散落在旧宿主中心、页面兜底、生命周期分支里。

## 4. 完成定义

全部满足才算完成：

1. `capabilityLifecycle.ts` 不再出现按具体软件写死的安装、探测、卸载分支。
2. 新增 `SoftwareBridgeDriver` 统一接口，driver 只返回事实结果，不直接写 lifecycle events。
3. 新增 `softwareBridgeRegistry`，统一负责注册、列出、匹配 driver。
4. Photoshop、Blender、Maya、Unreal 迁移为首批真实 driver。
5. `deriveSoftwareConnectionState()` 通过 registry 判断是否支持 bridge，不维护重复软件正则。
6. `GET /v1/capability-packages/drafts` 对 `software_connection` 返回 `connectionState`。
7. 连接页面优先消费后端 `connectionState`，不再写具体软件关键词兜底。
8. 未注册软件进入 `template_missing`，但仍保留启动、识别运行、对象对话、模板草稿生成路径。
9. `connected` 只能来自真实 probe 成功：`lastProbe.ok === true`。
10. 自动测试能证明：新增 fake driver 后，无需修改 lifecycle 主流程即可完成 install/probe/uninstall 调度。
11. Copilot 提示明确引导：新增软件连接时围绕 driver registry 和连接对象工作，不建议修改 lifecycle 主流程。
12. 修改 `local-companion/` 或 `companion-desktop/` 运行时代码后，执行本地 companion 重启。

## 5. 目标架构

允许的调用链：

```text
CapabilityPackage(type=software_connection)
  -> softwareBridgeRegistry.resolve(pkg)
  -> driver.install / driver.probe / driver.uninstall
  -> capabilityLifecycle 统一记录 lastInstall / lastProbe / events
  -> capabilityContext / drafts API 返回 connectionState
  -> connection-page 渲染状态、动作和下一步
  -> Copilot connection_loop_run 围绕同一个连接对象持续处理
```

禁止的调用链：

```text
capabilityLifecycle
  -> if Photoshop
  -> if Blender
  -> if Maya
  -> if Unreal
```

## 6. Agent 循环协议

每一轮 agent 必须按这个顺序执行：

1. Observe：读取本文件、`docs/连接改造执行状态.md`、相关源码、最近测试输出。
2. Select：选择第一个 `pending` 且依赖已完成的任务。
3. Act：只修改该任务列出的文件。只有测试或类型需要时，才允许增加相邻测试文件。
4. Verify：先跑任务列出的 focused checks，再按需要跑更宽检查。
5. Record：把任务结果追加到 `docs/连接改造执行状态.md`，包括文件、命令、结果、风险、下一任务。
6. Continue：检查通过则继续下一任务；遇到真实阻塞时按阻塞规则停下。

不要用口头判断代替证据。每个任务必须留下可复查的命令或人工验收记录。

## 7. 阻塞规则

1. 无关测试失败：记录失败命令、失败摘要、为什么和当前任务无关，然后继续以 focused checks 为准。
2. 缺少真实软件：自动测试继续完成，人工验收记为 pending，不伪造通过。
3. 需要用户选择真实目录、项目目录、管理员授权、登录态时，停止并说明需要的具体动作。
4. 同一任务连续三次出现同类失败，记录为 blocked，不扩大改造范围。
5. 架构语义不明确时，选择权限更小、不伪造成果、不污染云端版本的方案。

## 12. 最终架构审计问题

完成后必须逐条回答：

1. 新增一个软件连接时，是否无需修改 `capabilityLifecycle.ts`？
2. 新增一个软件连接时，是否只需要新增或注册 driver？
3. 未注册软件是否进入产品化 `template_missing`，而不是卡住？
4. 已注册软件是否都必须通过真实 probe 才能进入 `connected`？
5. 连接页面是否不再复制后端 driver 匹配逻辑？
6. Copilot 是否知道围绕连接对象和 driver registry 工作？
7. 自动测试是否能阻止架构回退到硬编码分支？

只有以上问题全部回答“是”，本改造才算完成。
