### 大图提交 Vertex 时「图片太大 / Body too large」

- **现象**：用户上传 3200x1338、6MB+ 图片后，工作区线稿/图生图在 Vertex 链路报「图片太大」或代理请求体超限。
- **原因**：图片进入代理前会转 base64 并包进 JSON；单图体积放大，叠加批处理时更容易超过请求体阈值。
- **修复**：前端在提交前自动做单图压缩兜底（优先不改像素，仅转 JPEG 质量降档），将每张入参图控制在 2MB 以内；覆盖理解阶段、单图生图、多图生图路径。
- **涉及**：`services/geminiService.ts`

### 左侧步骤缩略图树不跟时间线、重开后像「没了」

- **现象**：右侧「步骤时间线」仍按历史列出各步，左侧版本链缩略图只剩原图或整段空白；重开页面后更明显。

- **修复**：有 IndexedDB 时 **首屏 `activeWorkspaceProjectId` 先为 null**，hydrate 完成后再 **`loadWorkspaceProjectInternal` 一次性写入 id+assets**；各恢复分支去掉「先 setActive 再 load」；**`loadWorkspaceProjectInternal` 在未 ready 时先 `ensureWorkspaceBundlesHydratedFromIdb` 再加载**；**`openWorkspaceProject` 开头补 await hydrate** 以便切换前能保存上一项目；回收站恢复前同样 hydrate；bundle 解析失败打 **`console.warn`**。

### 全景贴回错位：解析式 lon/lat 与 Three 球面 UV 不一致

- **现象**：局部重绘结果贴回等距柱后，块与真实场景明显错位（平面模式对比更明显）；默认「正前方」也不像纹理水平中线。
- **原因**：`equirectNormFromSnapshotPixel` / `clientToEquirectNorm` 曾用 `lon = atan2(x,z)`、`v = 0.5 - lat/π`，与 **`THREE.SphereGeometry` 默认 UV**（`phi = atan2(z,-x)`、`v = 1 - acos(y)/π`）不一致，射线 → 纹理坐标映射错误；初始相机在 `(0,0,D)` 时视线朝 **-Z**，对应约 **u≈0.75**，不是 **u=0.5**（属查看约定，不一定是源图错）。
- **修复**：**`services/panoEquirectThreeMapping.ts`** 提供 **`directionToThreeSphereEquirectUv` / `threeSphereEquirectUvToDirection` / `wrap01PanoU`**；**`panoLocalInpaintPano`** 反投影与贴回循环改用上述映射；**`EquirectangularPanoramaCanvas`** 优先用 **`intersect.uv`**，否则 **`worldDirOnFlippedPanoSphereToEquirectUv`**；**`equirectNormToClient`** 用 **`equirectUvToWorldPosOnFlippedPanoSphere`**；默认/复位/双击相机 **`(DEFAULT_ORBIT_D, 0, 0)`** 朝 **-X**，正中为纹理 **u=0.5**（见下条 **scale(-1,1,1)**）。
- **补充**：球体 **`geometry.scale(-1, 1, 1)`** 只翻顶点、不翻 UV，世界 **+X** 侧表面显示的是原 **-X** 纹理（**接缝**）；若仅把相机放在 **-X** 朝 **+X** 看，正中仍是接缝，与「图水平正中」相差 **180°**。
- **补充（贴回上下翻转）**：**`SphereGeometry`** 的 **`uv.y`** 与 **`ImageData` 行索引**相反（顶行对应 **v→1**）。**`compositePanoPatchOntoEquirect`** 须用 **`iy = clamp(floor((1-vv)*nh), …)`**，不能 **`floor(vv*nh)`**。
- **补充（1k 底图 + 高清生成发糊）**：贴回在底图像素栅格上做 UV 映射，多 patch 像素会落同一格。抬升倍数取 **`max(patch/扩边框, patch/等距柱足迹)`**，**`estimatePanoPatchEquirectFootprintPx`** 用扩边框反投 UV 估足迹（模型常返回与裁切同尺寸，仅靠 patch/扩边框会为 1）；有单边/总像素/倍数上限；输出等距柱可能比原图大。
- **补充（贴回后出现极坐标状网格）**：前向 **patch 像素 → `floor` 等距柱格** 的 splat 易与球面映射叠加产生规则混叠。**`compositePanoPatchOntoEquirect`** 改为在输出等距柱足迹包围盒内 **逆映射**（`equirectUvToWorldPosOnFlippedPanoSphere` + `Vector3.project`）到快照浮点坐标，**双线性**采样 patch 再合成。
- **补充（全景贴回后预览极卡）**：① 取色缓冲已限边 **2048**；② **根因**：`EquirectangularPanoramaCanvas` 每帧 `tick` 都调用 **`subscribeAnimation`**，`ImageFlatAnnotationOverlay` 内 **`setLayoutTick`** 导致标注层 **60fps 全量 React 重绘**。改为仅当 **相机姿态/FOV/宽高比/帧缓冲尺寸** 相对上一帧变化时才通知监听者（`panoramaAnimSignature`）；`setOverlayPx` 同尺寸则跳过。
- **涉及**：`services/panoEquirectThreeMapping.ts`、`services/panoLocalInpaintPano.ts`、`components/EquirectangularPanoramaCanvas.tsx`

- **现象**：浏览器/设置里能访问 `127.0.0.1:18081/health`，工作区分割仍提示伴侣侧 `COMPUTE_SAM_BACKEND`。
- **原因**：本机若配置 **HTTP(S)_PROXY**，Node `fetch` 访问 `127.0.0.1` 可能被送去代理，连接失败，与 SamLocal 是否运行无关。
- **修复**：伴侣在 **`runSamSegmentJob` / `probeSamSegmentBackendHealth`** 前合并 **`NO_PROXY`/`no_proxy`** 包含 `127.0.0.1,localhost,::1`；桌面壳拉起子进程时同样注入。用户可托盘 **重新启动本地伴侣** 后重试。

### 全图自动分割却只高亮中心一小块（像只抠了一个物体）

- **现象**：大图跑「自动拆分」后，叠层只有画面中央附近一小块，不像官方 demo 满图多区域。
- **原因**：SamLocal `POST /v1/segment/predict` 仅在 **`returnAllMasks && multimaskOutput`** 时返回 JSON 多 mask；**`autoSegment` 单独为 true 时若未带 `returnAllMasks`**，会走 **单张 PNG** 分支，内部等价于 **无提示时在图像中心落默认前景点**，只分割中心附近一块。
- **修复**：路由改为 **`autoSegment` 为真时一律走多 mask JSON**（`_predict_multimask_response` → `generate_auto_masks_json` / stub 九宫格）。
- **涉及**：`SamLocal/app/main.py`

### 全图自动分割完成后主图上看不到任何分割块

- **现象**：自动拆分成功（日志有块数），但预览上无半透明叠层，像没生成。
- **原因**：合成 `lightboxSamPreviewCompositeHref` 时，`extra` 仅在 **已勾选** 或 **悬停** 时才把 mask 加入 `stack`；未勾选且未悬停时 `stack` 为空，叠层 href 被清空。

### 工作流报错：`Cannot read properties of null (reading 'previewLayers')`

- **现象**：顶部红条「工作流执行失败」，控制台/堆栈指向读取 `previewLayers` 时对象为 `null`。
- **原因**：`useEffect` 内写为 `lightboxSamUnsaved?.assetId === assetId && lightboxSamUnsaved.previewLayers...`。当 **`lightboxSamUnsaved === null`** 且 **`lightboxAsset?.id` 为 `undefined`** 时，`undefined === undefined` 为真，短路未拦住，继续访问 **`null.previewLayers`** 即抛错。
- **修复**：先取局部变量，用 **`unsavedSam && unsavedSam.assetId === assetId && ...`** 再读 `previewLayers`（或全程对 `lightboxSamUnsaved` 做存在性判断）。
- **涉及**：`components/WorkflowSection.tsx`（合成 `lightboxSamPreviewCompositeHref` 的 effect）

### 工作区 IndexedDB hydrate 后首屏不加载画布 / 原图「还原不了」（竞态）

- **现象**：有 IndexedDB 时，偶现打开上次项目后资产列表为空或长期空白；严重时磁盘 bundle 被写成空（原图/步骤似「丢失」）。
- **原因**：`ensureWorkspaceBundlesHydratedFromIdb` 完成后调用 `markWorkspaceLocalIdbHydrateReady()` 仅 `setState(true)`，**`workspaceLocalIdbHydrateReadyRef` 要等下一帧 `useEffect` 才为 true**；同一微任务内紧接着的 `loadWorkspaceProjectInternal` 因 `ref` 仍为 `false` **直接 return**，未执行 `loadWorkflowBundle` + `setWorkflowAssets`。随后 `workspaceLocalIdbHydrateReady` 变为 true 触发 **650ms debounce 自动 `trySaveWorkflowBundle`**，可能用空 `workflowAssets` **覆盖**已 hydrate 的内存/磁盘状态。
- **修复**：`markWorkspaceLocalIdbHydrateReady` 内 **同步** `workspaceLocalIdbHydrateReadyRef.current = true` 再 `setState`；在将 ready 置为 `false` 的各 effect 入口 **同步** `ref.current = false`。
- **涉及**：`App.tsx`

### 本地生图 Failed to fetch（公网代理 / CORS / 本机 9002）

- **现象**：工作区生图/线稿等失败，界面曾出现超长「Failed to fetch」排障文案；线上同配置可生、本地不行时 Network 里可能对 `*.onrender.com` 的 bulk 请求为 **(failed) net::ERR_FAILED** 或预检失败。
- **原因**：(1) **浏览器直连公网 gemini-proxy** 且 **`PROXY_ALLOWED_ORIGINS` 未含 `http://localhost:3000`** 等本地 Origin 时，**CORS** 在浏览器侧表现为 **`Failed to fetch`**。(2) 链路被墙/不稳定。(3) 已设 **`VITE_BULK_IMAGE_API=same-origin`** 但本机 **9002** 未起，Vite 反代 `/proxy/gemini` 连接被拒绝。
- **修复**：**方案 A**：`npm run dev` 下保持 **`VITE_BULK_IMAGE_API` 指向公网** 时，由 Vite **`/__ac-bulk-forward/{索引}/...`** 同源转发（**`vite.config.ts`** + **`services/geminiBulkForwardDevOrigins.ts`** + **`geminiService.bulkApiUrl`**）。**方案 B**：在代理侧把本地 Origin 加入 **`PROXY_ALLOWED_ORIGINS`**。**方案 C**：本地 **`VITE_BULK_IMAGE_API=same-origin`**（或 `1` / `true`）并 **`npm run dev:gemini-proxy`**（**`restart:local-stack`** 含 gemini）。改 Vite 变量后需重启 Vite。
- **涉及**：`vite.config.ts`、`services/geminiBulkForwardDevOrigins.ts`、`services/geminiService.ts`、`scripts/restart-local-stack.ps1`、`.env.example`、`services/trialGeminiQuota.ts`

### 生图 / 底部输入报「Maximum call stack size exceeded」

- **现象**：运行日志 `[WARN] [工作区] [底部输入] Maximum call stack size exceeded`；多出现在底部快捷栏生图或输入较长时。
- **原因**：(1) **`WorkspaceQuickComposeBar`** 中档位纠偏 **`useLayoutEffect` 将整颗 `genSettings` 放入依赖**，父级每次 render 传入新对象引用 → **每个 commit 后 layout 阶段都跑 effect**，与 `onGearId` 纠偏形成同步 setState 级联，极端下栈溢出。(2) **`capabilitySearchMatch.keywordContainsAnySubstringOfShortField`** 在 `fieldLower` 很长时内层循环次数与长度成正比，底部整句联动侧栏筛选时可能拖死或触发异常。(3) **大图 + 局部重绘锚点**：`lightboxAnchorClient` 在 **`ImageFlatAnnotationOverlay` 的 layout effect** 中每帧/子像素变化即 `setState`；快捷条 effect 又将 **`draft` 等** 绑进依赖 → **按键即 `setPosition`**，与叠层锚点更新形成 layout 级联，仍可能栈溢出或「卡死」。(4) 极端 **`asset.vgp` 深嵌套** 时 **`JSON.parse(JSON.stringify)`** 亦可触发同字面 RangeError（若仍出现需单独加固 `vgpStore.deepCloneVgp`）。
- **修复**：effect 仅依赖 **`gearId` / `onGearId`** 等稳定原语；子串匹配仅扫描 **`field` 前 32 字符**、关键字扫描 **`kw` 前 512 字符**；**父级锚点**坐标变化小于 **1px** 不更新 state；大图锚点定位 **去掉 `draft`/`promptCards.length` 依赖**，条高度变化用 **`ResizeObserver`** 再贴锚点；**`setPosition`** 位移小于 **1px** 则返回上一 state 引用。
- **涉及**：`components/WorkspaceQuickComposeBar.tsx`、`components/workflow/capabilitySearchMatch.ts`、`components/WorkflowSection.tsx`

### Windows 桌面壳 SamLocal 一键安装：下载权重 ENOENT（.partial）

### Tripo 图生 3D 提交 HTTP 413「请求体过大」

- **现象**：工作流生成 3D 失败，日志 `Tripo：HTTP 413 — {"error":"请求体过大"}`，多出现在高分辨率参考图（大图/PNG）拖入「生成3D」时。

- **涉及**：`services/tripoService.ts`、`services/tripoUploadImagePrep.ts`、`server/http-limits.js`、`server/auth-api.js`
