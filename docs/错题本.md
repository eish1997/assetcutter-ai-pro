# 错题本

记录开发与使用中出现的问题及修复方式，便于复现与排查。

## 使用说明

- **何时记**：报错、崩溃、逻辑与预期不符、线上/本地踩坑等。
- **怎么写**：现象 → 原因（若已知）→ 修复或规避 → 涉及文件/提交（可选）。
- 按时间**倒序**追加（最新在上），或统一用二级标题按日期分块。

## 2026-04

### 文字资产文生图后仍显示「文字」且无法拖入图生图/图像处理

- **现象**：文本资产生成图片后，卡片已切到图片版本，底部标识仍为「文字」；拖入图生图、图像处理等无效，像仍被当作纯文本。
- **原因**：`buildPendingTaskFromAssetSnapshot` 对 `assetKind === 'text'` 一律只允许 `workflowPresetAcceptsTextCardDrag`（文生文/文生图），图类能力入队直接 `return null`；底部 `getAssetDisplayTypeLabel` 对文字卡恒返回「文字」。
- **修复**：文字卡允许在「当前展示为 `results` 中的位图版本」且通过 `workflowAssetAllowedForCapabilityDrop` 时，为图类能力建任务；拖入过滤与「能力块→卡」校验与之一致；`getAssetDisplayTypeLabel` 在非 `original` 且 `results[displayKey]` 为位图时显示对应步骤标签。
- **涉及**：`components/WorkflowSection.tsx`

### 3D 模型卡片不更新单帧缩略图、灯箱「平面」预览发糊

- **现象**：导入 GLB 后后台已把 `original` 换成 JPEG，网格仍像占位；大图元数据约 512×320，放大很糊。
- **原因**：`ProgressivePreviewImage` 的 `cacheKey` 仅用 `id + displayKey`，占位 SVG 阶段生成的微图/小图缓存在 LRU 中；`original` 替换后键不变，一直命中旧缓存。另快照默认 512×320、JPEG 0.86，用作灯箱平面图源偏小。
- **修复**：`previewSrcCacheFingerprint(src)` 并入工作区/仓库网格 `cacheKey`；离屏快照默认 **1280×800、JPEG 0.9**；含 `modelUrls` 的卡片 `thumbMaxEdge` 提到 **896**。
- **涉及**：`services/workflowImageThumb.ts`、`services/workflowModelPreviewCapture.ts`、`components/WorkflowSection.tsx`

### Antigravity 文生图 HTTP 404「Requested entity was not found」

- **现象**：工作区执行文生图（或标准/Pro 挡位生图）日志含 `Upstream error 404`、`Requested entity was not found`；对话文字仍正常。
- **原因**：Antigravity 生图 **`passthroughModels`** 原样透传站内 id（如 `*-preview`），与反代控制台登记的 **模型 ID**（如 `gemini-3.1-flash-image`、`gemini-3-pro-image`）不一致即 404。
- **修复**：`resolveUpstreamImageModelId` 在供应商为 **`antigravity`** 时：`gemini-3.1-flash-image-preview` → `gemini-3.1-flash-image`，`gemini-3-pro-image-preview` → `gemini-3-pro-image`（与 Antigravity「API 反代」页一致）。**VectorEngine** 仍回退 `gemini-2.5-flash-image`；**ToAPIs** 不改此函数。
- **涉及**：`services/geminiService.ts`

### Antigravity（及 ToAPIs / VectorEngine）下「文字正常、生图不走反代」

- **现象**：设置里选 Antigravity 后对话/理解正常，生图失败或行为像 Vertex/官方代理。
- **原因**：配置了 `VITE_BULK_IMAGE_API` 时，`dialogGenerateImage` 原先用 `BULK_BASE` 判断即走 `enqueueImageBatchGenerateContent` → 后端 `gemini-proxy` 批量队列，**未**调用 `getAI()` 的浏览器侧网关适配层。
- **修复**：新增 `shouldUseBulkImageBatchQueue()`：仅 Vertex、或「官方 Gemini 路径且应走后端代理」时入队；`toapis` / `antigravity` / `vectorengine` 始终直连各自 `getAI()` 生图。
- **涉及**：`services/geminiService.ts`

### 文字资产切到扩写版本后执行能力仍使用原始正文

- **现象**：在文字资产中切到扩写版本后执行「变体/文生图」等能力，实际输入仍是原始正文，结果与当前显示版本不一致。
- **原因**：`workflowAssetToInputText` 仅拼接 `textTitle + textBody`，未按 `displayKey` 读取 `textResults[displayKey]`。
- **修复**：`workflowAssetToInputText` 改为优先读取当前 `displayKey` 对应文本（`original` 走 `textBody`，其它版本走 `textResults`），缺失时回退原始正文；并新增单测覆盖当前版本与缺失回退两条路径。
- **涉及**：`services/workflowTextAsset.ts`、`tests/workflowTextAsset.test.ts`

### 文生文生成数量“看起来没生效”（未自动分组复制）

- **现象**：文生文分组已出现“生成数量”按钮，但数量>1时没有像生图那样自动分组并复制资产卡片。
- **原因**：数量扩增函数 `expandRootAssetsForGenerateCount` 对文字资产有硬过滤（`isWorkflowTextAsset` 直接跳过）；且自动成组函数默认也过滤文字资产，导致文生文仍走单卡路径。
- **修复**：为数量扩增与自动成组增加“允许文字资产”开关；文生文（`text_to_text`）启用该开关后，数量>1时与生图一致：复制资产卡片 + 自动成组 + 各卡片分别回填结果。
- **涉及**：`components/WorkflowSection.tsx`

### 文字资产弹层「只能框选、无法输入」

- **现象**：打开文字资产后正文区域只能框选文本，无法直接输入编辑。
- **原因**：UI 改版后默认进入预览态（`editing=false`），且弹层内鼠标事件会继续冒泡到底层工作区，触发框选手势干扰输入。
- **修复**：打开弹层默认进入编辑态；在弹层根节点增加 `onMouseDownCapture` / `onPointerDownCapture` 阻断事件冒泡，避免底层框选抢占交互。
- **涉及**：`components/workflow/WorkflowTextAssetOverlay.tsx`

### Vertex 同批生图出现「两个成功两个失败：The operation was cancelled.」

- **现象**：同一批（如 4 张）里部分成功、部分失败，失败日志为 `The operation was cancelled.`。
- **原因**：批处理内每一项最终仍是单独 Vertex 请求；原单项超时默认 120s，慢项会被提前取消；且该报错未纳入重试判定，导致直接失败返回。
- **修复**：将 Vertex 单项生图超时下限提高到 300s（`GEMINI_VERTEX_IMAGE_TIMEOUT_MS`）；前端与代理端均将 `The operation was cancelled / canceled / CANCELLED` 视为可重试错误并走退避重试。
- **涉及**：`services/geminiService.ts`、`server/gemini-proxy-api.js`

### Antigravity 日志「All accounts exhausted」+ cloudcode-pa / error sending

- **现象**：工作区 `[拆分组件] … All accounts exhausted. Last error: HTTP request failed at https://cloudcode-pa.googleapis.com/v1internal: error sending…`
- **原因**：Antigravity-Manager 反代在轮换账号后仍无法成功请求 **Google Cloud Code 上游**（多为运行反代的机器访问 Google 失败：网络、代理未覆盖、防火墙、Token/配额等），**非本站请求体格式问题**。
- **处理**：在本机排查 Antigravity-Manager 账号状态、系统/终端代理、能否直连 `cloudcode-pa.googleapis.com`；站点侧已对同类错误附加简短中文说明，并在非 JSON 错误体时保留原文。

### Antigravity 下「拆分组件」创建图像任务失败（502）

- **现象**：`创建图像任务失败（502）`（`POST …/images/generations`）。
- **原因**：（1）文生图 JSON 路径：`size`/`metadata` 与反代 OpenAI 映射不一致（已用 WxH + `quality`、去掉 ToAPIs `metadata`）。（2）**更关键**：GitHub `handle_images_generations_internal` **从不读取 `image_urls`**，参考图不会进上游；图生图须 **`POST /v1/images/edits`（multipart，`image1`…）**（`handle_images_edits`）。
- **修复**：`skipToapisImageUpload` 且**有参考图**时改调 **`/images/edits`**；无参考图仍 **`/images/generations`**；ToAPIs 仍 uploads + `image_urls` + generations。
- **涉及**：`services/toapisAdapter.ts`

### Antigravity 下图生图报「上传参考图失败（404）」

- **现象**：`上传参考图失败（404）：响应体为空或非 JSON`（日志仍可能带 `[拆分组件]`：裁剪后若执行方式为「生图」会再走 `dialogGenerateImage`）。
- **原因**：ToAPIs 适配层图生图会先 `POST /v1/uploads/images` 换 HTTPS URL；**Antigravity 通常无此路由**，故 404。
- **修复**：`skipToapisImageUpload: true` 跳过 uploads；有参考图时走 Antigravity **`/images/edits` multipart**（`image1`…），文生图仍 **`/images/generations`**；并支持同步 `data[0].b64_json` / `url`。
- **涉及**：`services/toapisAdapter.ts`、`services/geminiService.ts`

### Antigravity 下「拆分组件」报 Failed to execute 'json' on 'Response'（根因多为走错 SDK）

- **现象**：同上，且用户以为已选 Antigravity。
- **根因**：`getAI` 在供应商为 `antigravity`/`toapis`/`vectorengine` 但**未填对应 Key** 时，会**继续落到** `GoogleGenAI`（若本机还填了 Gemini Key）；`@google/genai` 浏览器包对 HTTP 响应调 `response.json()`，空 body 即抛此错。另：`ac_ai_provider` 大小写与云端 JSON 不一致时曾误判为 `gemini`。
- **修复**：上述三供应商**缺 Key 时直接抛中文说明**，不再回退官方 SDK；`getAiProvider` 与云端 `user-config` 拉取/推送对 `aiProvider` **trim + toLowerCase**；`toapisAdapter` 上传/轮询/建图任务用 `readResponseJson`（`text` + `parse`）替代 `res.json()`。
- **涉及**：`services/geminiService.ts`、`services/settingsStore.ts`、`services/workspaceUserCloudConfig.ts`、`services/toapisAdapter.ts`

### Antigravity 下「拆分组件」报 Unexpected end of JSON input / Response.json

- **现象**：`Failed to execute 'json' on 'Response': Unexpected end of JSON input` 或同类 JSON 解析错误。
- **原因**：反代返回 **空 body**，或默认 **流式 SSE**（正文为多行 `data: …`），对整段 `JSON.parse` 失败；空串时浏览器/引擎报错文案常带 `Response`。
- **修复**：`toapisAdapter` 的 chat 请求显式 **`stream: false`**；`parseOpenAiChatCompletionsBody` 对空正文给出明确错误；解析失败时若含 `data:` 则按 SSE 聚合 `delta.content` / `message.content`。
- **涉及**：`services/toapisAdapter.ts`

### Antigravity 下「拆分组件」报 ` ```json ` 非合法 JSON

- **现象**：`Unexpected token '`', "```json` … is not valid JSON`。
- **原因**：OpenAI 兼容路径仅能用 `response_format: json_object`，模型仍常输出 **markdown 代码块** 包裹的数组；`detectObjectsInImage` 原先用 `JSON.parse` 整段文本。
- **修复**：`parseBoundingBoxJsonArrayFromModelText` 剥 ``` / ```json 围栏，失败时再截取首个 `[`…`]` 子串再 parse。
- **涉及**：`services/geminiService.ts`

### Antigravity 下「拆分组件」等报 HTTP 404 / All accounts exhausted

- **现象**：工作区日志 `[拆分组件] … All accounts exhausted`，附 `HTTP 404`、`Requested entity was not found`。
- **原因**：Antigravity 复用 `createToapisGeminiClient` 时仍走 ToAPIs 的模型名改写（如 `gemini-3-flash-preview` → `gemini-3-flash-preview-official`），上游无此模型则 404，网关轮询账号后报 exhausted。
- **修复**：Antigravity 路径使用 `createToapisGeminiClient(..., { passthroughModels: true })` 原样提交站内模型 id；若仍 404，在 Antigravity「模型路由」把站内 id 映射到网关支持的名称。
- **涉及**：`services/toapisAdapter.ts`、`services/geminiService.ts`

### 用户配置推送 /upload-url 返回 400「必须提供 contentLength」

- **现象**：控制台 `[workspace cloud] user config push HttpRequestError`，或 Network 里 `POST .../api/r2/upload-url` 为 400，文案含「上传工作区图片必须提供 contentLength」。
- **原因**：`user-config.json` 落在 `users/.../workspace/` 下，服务端按**可计费工作区对象**校验，预签名前必须带 **contentLength**；`pushWorkspaceUserCloudConfig` 与 `workspaceCloudSync` 的 `putObjectBytes` 此前未传该字段（工作流图片打包路径 `workspaceR2ImageBundle` 已正确传入）。
- **修复**：上述两处请求体增加与 PUT 正文一致的 **UTF-8 字节长度**（string 用 `TextEncoder`；`ArrayBuffer`/`Blob` 用 `byteLength`/`size`）。
- **涉及**：`services/workspaceUserCloudConfig.ts`、`services/workspaceCloudSync.ts`

### 工作区生图报 403 PERMISSION_DENIED（Google project denied access）

- **现象**：日志或界面出现 `{"error":{"code":403,"message":"Your project has been denied access...","status":"PERMISSION_DENIED"}}`（能力名如「变体」仅来自预设 `label`）。
- **原因**：**Google 侧**拒绝当前 **API Key 所属 Cloud / AI Studio 项目**使用 Gemini（欠费、条款限制、项目被封禁、未开通相关 API 等），非本站业务逻辑错误。
- **修复/规避**：在 Google AI Studio / Cloud Console 检查项目与计费并**更换有效 Key**；或走**后端代理**（`VITE_BULK_IMAGE_API` + 服务器 `GEMINI_API_KEY`）；或使用设置里已支持的**第三方网关**（ToAPIs / VectorEngine 等）。
- **涉及**：`services/geminiService.ts`（`normalizeApiErrorMessage` 对 403 给出中文说明）、`services/capabilityExecutor.ts`（能力失败信息走规范化文案）

### 对话内生成图/附图只露一条、会话行无模糊底图

- **现象**：全景等宽图在气泡里像被裁成一条；左侧会话仍纯色底，无「最后一张生成图」模糊背景。
- **原因**：助手结果外层用了 **`aspect-ratio` + 内层 `min-h-[8rem]`**，子级撑高超过比例盒，`overflow-hidden` 只露出顶部一条；会话行只在内存里有 **`resultImageBase64`** 时才画背景，持久化后常 **仅有 R2 key**，`img` 无 src。
- **修复**：助手结果盒 **去掉内层 min-h**，比例盒加 **`maxHeight: min(85dvh,920px)`**；用户附图 **`max-h` 提到 min(70dvh,720px)**、缩略解码边加大；新增 **`DialogSessionRowBackdrop`**，对 **仅有 objectKey** 时 **`downloadR2ObjectAsDataUrl` 拉取**后再模糊；用户消息若 **无文字仅有图** 显示一句占位说明。
- **涉及**：`App.tsx`、`components/DialogSessionRowBackdrop.tsx`

### 会话标题行看不到生成图底图（像纯色块）

- **原因**：`DialogSessionRowBackdrop` 在模糊图之上叠了 **`/90~93` 不透明** 的整层蒙版，把底层图几乎完全盖住。
- **修复**：提高底图 **`opacity`**、略加大 **`blur`**；蒙版改为 **`bg-gradient-to-r`（左深右淡）**，保证标题区对比度、右侧仍能看出最后一张生成图。
- **涉及**：`components/DialogSessionRowBackdrop.tsx`

### 跟进：超宽全景仍被裁成一条

- **原因**：`ProgressivePreviewImage` 在固定 **`aspect-ratio` + `max-height`** 的盒内绝对定位，`object-contain` 仍受 **外层气泡 `overflow-hidden`** 与比例计算影响，易出现只看见局部。
- **修复**：对话内 **用户附图 + 助手生成图（含识别框分支）** 改为 **`SiteImage`** 直链展示：`max-w-full` + `max-h-[min(90dvh,960px)]` + `w-auto h-auto object-contain`，去掉比例盒与渐进缩略；助手/用户气泡统一 **`overflow-visible`** 避免圆角容器裁切。
- **涉及**：`App.tsx`（`AppMode.DIALOG`）

### 左侧无会话行、对话区无用户消息但仍在「生图中」

- **现象**：会话列表只剩「更早的对话」折叠标题或空白；中间无自己的气泡，底部仍显示理解/生图状态。
- **原因**：① `updatedAt` 缺失或非数字时 `now - s.updatedAt` 为 **NaN**，既不满足「最近」也不满足「更早」，**所有未归档会话被过滤掉**。② 持久化的 `activeSessionId` 指向**已不在列表中的会话**时，`activeSession` 为 undefined → `dialogMessages` 恒为空，且 `setDialogMessages` 按 id 更新**匹配不到任何会话**，发送后消息也进不了列表。
- **修复**：载入与 R2 hydrate 后对每条会话 **`normalizeDialogSession`**（补全 `createdAt`/`updatedAt`）；`useEffect` 校验当前 id 是否在 `dialogSessions` 中，否则回退到第一项；「更早的对话」**默认展开**；列表排序/时间展示用 **`activityAt` 安全取值**。
- **涉及**：`hooks/useDialogWorkspace.ts`、`App.tsx`

### 对话区生成图不显示（按钮与文案在，中间无图）

- **现象**：助手消息里「已根据你的需求生成图片」与下载等按钮可见，大图区域空白；右侧临时库仍有缩略图。
- **原因**：`ProgressivePreviewImage` 在大图 data URL 时走「微图/小图」双绝对定位层，父级仅有 `relative inline-block max-w-full`、**无确定高度**，绝对子元素不参与撑高，容器高度为 0，看起来像「没图」。
- **修复**：助手结果外包一层带 **`aspectRatio`（有宽高元数据时）或 `min-h-[14rem]`** 的容器；用户消息附图网格同样为每张图加 **`min-h` + `max-h`** 包裹。对话内解码优先级设为 `high`。
- **涉及**：`App.tsx`（`AppMode.DIALOG` 消息渲染）

### 跟进：会话标题/用户气泡文字「看不见」

- **现象**：左侧会话标题不显示；用户侧对话文字像消失。
- **原因（推断）**：会话行把模糊图+`backdrop-blur` 与标题叠在同一 `<button>` 内，**层叠上下文**下部分环境会把文案盖在效果层之下；用户气泡 **`overflow-hidden` + 过高 `min-h` 附图区** 与 **`h-full` 百分比高度** 组合可能带来异常裁剪或可读性问题。
- **修复**：会话行改为**外层 `div` + `isolate`**，背景图为 **`z-0` 绝对层**，标题区为**独立 `type="button"`、`z-[1]`**，去掉 `backdrop-blur`；用户气泡 **`overflow-visible`**（附图区单独 `overflow-hidden`），文案显式 **`text-white` + `whitespace-pre-wrap`**，附图 **`min-h-32`**、去掉子级 `h-full`。
- **涉及**：`App.tsx`（会话列表 + 用户消息气泡）

### 批处理「排队中」无 ×：任务只在 `pending` 不在本批 `executingQueue.tasks`

- **现象**：已有任务执行/排队时新拖入能力，卡片中央显示「排队中」但无取消按钮。
- **原因**：`busy` 来自 `pending`，而新任务未并入当前批次的 `executingQueue.tasks`；原逻辑只在 `taskForRootSlot`（本批 tasks）存在且非 active 时渲染 ×，故 `taskForRootSlot === null` 时不显示。
- **修复**：根卡与组内槽位增加 `pendingTaskFor*`；若 `executingQueue` 存在、存在对应 `pending` 且其 `id` 不在本批 `tasks`，且本槽位无「批内排队」取消目标时，同样显示 ×，点击用 `setPending(filter)` 移除；批内排队仍走 `cancelQueuedTaskInBatch`。
- **涉及**：`components/WorkflowSection.tsx`

### 浏览器标签页 Out of Memory（全景 / 大图）

- **现象**：Chrome 提示「喔唷，崩溃啦」错误代码 Out of Memory；Network 里大量图片与 base64。
- **原因**：全景用 `TextureLoader` 将原图整分辨率上传 GPU，叠加 mipmap；工作流中常见超大图或 `data:image/...;base64`，解码 + 显存暴涨。
