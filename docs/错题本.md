### 2026-07-16: AI Gateway route candidates must include ops pause and key readiness
- Symptom: A model could be published and visible in the workspace, but task creation still failed later with no usable provider route.
- Cause: Route validation returned only the first matching provider. Disabled providers were not fully removed when no fallback existed, and OpenAI-compatible models could stop at `openai-official` even when only `toapis` had a usable key.
- Fix: Shared Gateway route resolution now exposes all executable candidates, filters disabled providers before planning, and route guards choose the first key-ready provider. Auth, HTTP, retry, and availability summary paths now use the same candidate logic.
- Regression: Cover Gemini fallback, OpenAI-compatible secondary-provider fallback, disabled single-provider routes, and admin availability status.

### 2026-07-16: AI Gateway job creation must recover stale credits reserve once
- Symptom: Bottom input text generation failed with `CREDITS_RESERVE_INVALID`; users were told to refresh before retrying.
- Cause: Unified Gateway creation reused cached `X-AC-Credits-*` headers from a previous task. Legacy AI Worker Proxy paths already refreshed once on invalid reserve, but `createAiJob` did not.
- Fix: `createAiJob` now catches `CREDITS_RESERVE_INVALID` once, clears local reserve cache, strips stale `X-AC-Credits-*` headers, and retries job creation so the server can issue a fresh reserve.
- Scope: Applies to text, image, video, and 3D Gateway jobs because they share `createAiJob`.

### 2026-07-16: Workspace model publish config must be durable
- Symptom: Admin supplier model checkboxes appeared saved, but re-entering the provider page reset them and the workspace did not show the selected models.
- Cause: `model-ops-config` was persisted only to `server/data/model-ops-config.json`. Online deployments can lose local disk state or serve reads/writes from different instances, so admin publication was not a true durable setting.
- Fix: `model-ops-config-store` now follows the same DB-first pattern as other gateway ops stores: Postgres when `DATABASE_URL` is available, disk fallback for local/dev, and auth startup ensures the table exists.
- Scope: Admin save, public `/api/model-ops-config`, workspace selectors, and gateway publication guards now read the same durable source.

### 2026-07-17: AI Gateway transient Postgres handling must include admin/observability paths
- Symptom: Online generation could still surface raw Postgres recovery errors after the main job store, key store, and settlement paths had retry guards.
- Cause: Secondary AI Gateway paths such as provider key health event queries and trend snapshot reads/writes still called Postgres directly. These paths can run near task creation, admin refreshes, or observability refreshes and leak transient database errors.
- Fix: Wrap AI Gateway provider key health listing/summary queries and trend snapshot ensure/save/list calls with `withAiGatewayPostgresRetry`. Keep auth/login DB behavior conservative; do not globally monkey patch `pg`.
- Regression: Gateway settlement tests must disable real execution when asserting reserve/finalize behavior, otherwise execution failure can immediately release the reserve and make the test look like reserve never happened.
- Follow-up: Usage billing and platform reserve settlement are part of the same generation chain. Wrap usage event ensure/insert/list and reserve acquire/release/batch settlement with the same retry helper so successful upstream generation is not marked failed during a short Postgres recovery window.

### 2026-07-17: Render Postgres outage must not fall back to local auth JSON
- Symptom: Render Postgres was resumed but stayed `unavailable`; the admin UI appeared to show only 3 users although production data still had 40 users.
- Cause: The production auth API could fall back to the local `auth-db.json` when Postgres was unavailable, which made an infrastructure outage look like user data loss. The database itself was also on a 1GB disk and remained unavailable after resume until storage was increased.
- Fix: Keep auth-api process alive for Render health checks, but return 503 for DB-backed routes while Postgres is unavailable. Disable production JSON fallback for auth data. Increase Render Postgres disk from 1GB to 5GB and enable disk autoscaling; after recovery, verify direct Postgres connection and `users` count.
- Regression: Auth startup tests should cover the production-unavailable path: the port opens, login returns 503 during the outage, and no local JSON auth store is used.
