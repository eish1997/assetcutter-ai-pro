# 连接对象卡片实现规格

更新时间：2026-08-11

## 1. 目标

把连接页的 `software_connection` 卡片改造成真正的“连接对象卡片”：

- 普通用户一眼看到：这是什么软件、当前启动哪个版本、现在是否可用、下一步做什么。
- 多个本机软件版本统一归到同一连接对象下，通过轻量版本抽屉切换。
- 已打开或已安装的软件可被自动识别，并合并到已有连接卡或创建新连接卡。
- UI 采用 Figma 中 `Connection Object Card Design / 连接对象卡片` 与 `Connection Version & Discovery Pattern / 版本切换与自动识别` 的方向：弱边框、少颜色、图标按钮、低干扰维护摘要。

非目标：

- 不重建旧“宿主中心”。
- 不把本机软件版本当成云端连接能力版本。
- 不把本地探索历史自动沉淀为云端版本。
- 不在卡片主区展示大段 facts、strategy、logs、模板草稿或错误堆栈。
- 不在 `capabilityLifecycle.ts` 增加具体软件硬编码分支。

## 2. 当前约束

- 仓库存在较多并行改动，执行时不得回滚无关文件。
- 连接主线已经是 `CapabilityPackage(type=software_connection)`，旧 host catalog 不应恢复。
- 软件版本事实当前已有 `ConnectionFacts.version`，拖拽创建时已有 `manifest.softwareVersion/versionHint`。
- 云端连接能力版本已有 `capabilityCloudVersions`，只用于管理员发布、切换、回滚。
- 连接页当前实现位于 `companion-desktop/shell/connection-page.js`，测试位于 `tests/shellConnectionPageUi.test.ts`。
- 本地伴侣运行时代码变更后需要执行 `npm run restart:local-companion`。

## 3. 术语

| 术语 | 含义 | 示例 |
| --- | --- | --- |
| 连接对象 | 一个 `software_connection` 能力包，代表“AssetCutter 与某类本机软件的连接” | Maya 随机选择连接 |
| 本机软件版本 | 用户电脑上某个软件安装或运行版本 | Maya 2022、Blender 4.2 |
| 当前启动版本 | 连接对象默认用于启动、探测、安装的本机版本 | Maya 2022 |
| 已识别版本 | 系统从拖拽、进程、快捷方式、注册表、常见目录发现的版本 | Maya 2020、Maya 2024 |
| 连接能力版本 | 连接对象的云端治理版本 | v1.0.2 |
| 维护摘要 | 面向用户的短状态芯片，不是诊断日志 | 信号OK、待信号、未验证 |

## 4. 产品规则

### 4.1 卡片主区

主区只能显示：

1. 软件名称。
2. 连接状态。
3. 当前启动版本。
4. 当前启动位置。
5. 下一步。
6. 最多 3 个图标主动作。

主区不得显示：

- facts 明细。
- strategy 明细。
- candidate strategies 列表。
- bridge template 草稿。
- 大段事件日志。
- 多个本机版本完整列表。
- 云端历史版本列表。

### 4.2 颜色与视觉

- 卡片边框使用弱灰色，不使用状态色描边。
- 页面主色控制为黑白灰 + 单一蓝色强调。
- 只有主动作 `Copilot` 使用蓝色。
- 状态、维护摘要使用低饱和灰色芯片。
- 错误态可以局部使用低饱和红色，但不能整卡变红。

### 4.3 图标动作

卡片底部使用图标按钮：

| 动作 | 图标语义 | 可见文字 |
| --- | --- | --- |
| Copilot 继续处理 | shield/plus 或 sparkle | 不显示，tooltip 显示 |
| 启动当前版本 | external-link / launch | 不显示，tooltip 显示 |
| 探测当前版本 | target / scan | 不显示，tooltip 显示 |
| 提交云端 | cloud-upload | 不显示，tooltip 显示 |
| 卸载桥接 | trash | 不显示，tooltip 显示 |

低频动作进入二级菜单或详情页，不挤在主卡。

### 4.4 多版本规则

- 卡片主区只显示当前启动版本。
- 点击“切换版本”入口打开版本抽屉。
- 版本抽屉展示所有已识别本机版本。
- 切换本机版本只改变本机启动目标，不创建云端连接能力版本。
- 选择某版本后，可执行：启动所选版本、探测所选版本、设为默认版本。
- 未验证版本可以显示，但不得标记为 connected。

### 4.5 自动识别规则

识别来源：

- 正在运行的进程。
- 用户拖入的 exe / lnk。
- 常见安装目录。
- Windows 注册表。
- 已保存的自定义目标。

归并规则：

- 能稳定判断同一软件时，新版本合并到同一连接对象。
- 无法判断同一软件时，创建新的未知软件连接草稿。
- 合并时不得覆盖用户当前默认版本，除非用户明确选择“设为默认”。
- 新识别版本状态默认为 `detected` 或 `unverified`，真实探测成功后才可变为 `verified`。

## 5. 数据模型

### 5.1 Manifest 扩展

在 `software_connection` 的 `manifest` 中新增或规范以下字段：

```ts
type LocalSoftwareVersion = {
  id: string;
  label: string;
  softwareVersion: string;
  executablePath?: string;
  shortcutPath?: string;
  installRoot?: string;
  source: 'drag_drop' | 'process' | 'registry' | 'common_path' | 'manual' | 'saved_target';
  status: 'detected' | 'launchable' | 'installed' | 'verified' | 'failed';
  lastSeenAt?: string;
  lastProbeAt?: string;
  verifiedStrategyId?: string;
};

type SoftwareConnectionManifest = {
  softwareVersion?: string;
  versionHint?: string;
  currentLocalVersionId?: string;
  defaultLocalVersionId?: string;
  localVersions?: LocalSoftwareVersion[];
};
```

兼容规则：

- 如果 `localVersions` 为空，但存在 `softwareVersion/versionHint/executablePath`，运行时派生一个 legacy local version。
- `manifest.version` 仅作为旧数据兼容读取，不再写入新软件版本。
- 能力包顶层 `version` 继续表示连接能力版本，不参与本机版本选择。

### 5.2 API 输出

连接页需要从能力包上下文拿到：

```ts
type ConnectionCardView = {
  id: string;
  name: string;
  statusLabel: string;
  currentLocalVersion: LocalSoftwareVersion | null;
  localVersions: LocalSoftwareVersion[];
  cloudVersionLabel?: string;
  nextActionLabel: string;
  maintenanceChips: Array<{ label: string; tone: 'neutral' | 'info' | 'ok' | 'warn' | 'bad' }>;
  primaryActions: Array<'agent_loop' | 'launch' | 'probe' | 'publish'>;
};
```

## 6. Definition Of Done

架构完成必须同时满足：

- `software_connection` 支持多个本机软件版本，并能稳定得到 `currentLocalVersion`。
- 本机软件版本与云端连接能力版本在数据模型、UI 和发布逻辑中分离。
- 连接卡片主区符合 Figma 低饱和图标卡片方向：弱边框、少颜色、图标按钮、当前版本单独显示。
- 版本抽屉可以查看、选择、启动、探测和设为默认本机版本。
- 自动识别可以把已运行或已安装的软件版本加入连接对象。
- 真实 probe 成功前不会把连接状态标记为 `connected`。
- 新增软件或新版本不得要求修改 `capabilityLifecycle.ts` 的具体软件分支。
- 所有任务均在执行记录中留下文件、命令、结果、残留风险和下一任务。

## 7. Agent Loop Protocol

每个任务按以下循环执行：

1. **Observe**：读取本规格、`docs/连接改造执行状态.md`、相关源码和最新测试输出。
2. **Select**：选择第一个依赖已完成的 pending 任务。
3. **Act**：做满足该任务的最小改动。
4. **Verify**：先跑任务内聚焦验证，再跑必要的页面测试或类型检查。
5. **Record**：在本文件“执行记录”追加任务状态、改动文件、命令结果、残留风险。
6. **Continue Or Stop**：验证通过继续下一项；遇到真实软件、权限、产品不确定性时按 blocked 规则处理。

选择任务规则：

- 只选择 `Status: pending` 且依赖已完成的最前任务。
- 如果当前任务失败，最多修复三轮；同一失败三次后按 blocked 处理。
- 不允许跳过 P0 数据模型直接做 P1 UI。
- 不允许用截图或主观判断替代自动测试。

记录规则：

- 每完成或阻塞一个任务，都必须追加一条执行记录。
- 记录必须包含：任务 id、状态、改动文件、命令、结果、手动证据、残留风险、下一任务。
- 如果只改文档，也要记录“未运行测试”的原因。
