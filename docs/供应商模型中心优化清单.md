# 供应商模型中心优化清单

**日期**：2026-07-15  
**状态**：优化建议稿  
**关联文档**：
- `docs/供应商模型中心架构设计.md`
- `docs/多模型可运营改造计划.md`
- `docs/模型中心与供应商绑定改造清单.md`

---

## 1. 当前主要问题

供应商中心的展示层已经先行建立，但后端执行能力、模型发布状态、Key 池、BYOK、计费和健康状态还没有完全对齐。

当前最容易产生误解的是：

- 前端能看到供应商，不代表后端 adapter 已接通。
- 供应商能配置 Key，不代表平台 Key 已用于真实任务。
- 模型在目录里，不代表已经发布到工作台。
- 同一个模型名由多个供应商提供，不代表能力、参数和价格完全一致。

所以后续优化的核心目标是：**把“展示、配置、验证、发布、执行、计费”分清楚。**

---

## 2. 供应商状态分层

供应商不应该只有“启用/停用”。建议拆成以下状态字段：

| 字段 | 含义 | 示例 |
|---|---|---|
| `catalogVisible` | 是否在供应商中心展示 | 火山方舟已展示 |
| `keyPoolSupported` | 是否允许管理员配置平台 Key | Tripo、即梦、方舟 |
| `backendAdapterReady` | 后端 adapter 是否已接通 | Tripo、即梦已接 |
| `platformKeyReady` | 是否真实使用平台 Key 执行任务 | Tripo、即梦 |
| `byokSupported` | 是否支持用户自带 Key | OpenAI、ToAPIs、方舟 |
| `modelCatalogReady` | 是否有模型清单 | 静态清单/扫描清单 |
| `smokeTestReady` | 是否支持测试连接/测试模型 | 待补 |

供应商中心 UI 应明确显示这些状态，避免管理员误以为“能看到供应商 = 已可用”。

---

## 3. 模型状态分层

Provider Model 和 Canonical Model 都需要状态，但含义不同。

### Provider Model 状态

| 状态 | 含义 |
|---|---|
| `discovered` | 扫描或静态发现，未验证 |
| `testing` | 待测试或测试中 |
| `verified` | 已通过最小调用验证 |
| `deprecated` | 官方废弃或不建议继续用 |
| `disabled` | 平台停用 |

### Canonical Model 状态

| 状态 | 含义 |
|---|---|
| `draft` | 平台内部草稿 |
| `published` | 工作台可选 |
| `deprecated` | 已不推荐新任务使用 |
| `disabled` | 完全下架 |

注意：`ProviderModel.verified` 不等于 `CanonicalModel.published`。供应商模型可用之后，还需要管理员决定是否发布给工作台。

---

## 4. Route 状态与能力差异

同一个 canonical model 可以有多个供应路径，例如：

- `gpt-image-2 -> OpenAI`
- `gpt-image-2 -> 火山方舟`
- `gpt-image-2 -> ToAPIs`

但这些路径不能默认等价。Route 至少应维护：

- `enabled`
- `priority`
- `fallbackPolicy`
- `requiresEndpointMapping`
- `parameterMappingRef`
- `limits`
- `costProfile`
- `qualityTier`
- `lastSmokeTestAt`
- `lastErrorAt`

尤其是 OpenAI-compatible 供应商，虽然协议兼容，但具体参数、模型 ID、endpoint、返回结构、审核策略和价格都可能不同。

---

## 5. Key 池与 BYOK 边界

平台 Key 池和用户 BYOK 必须清晰分开。

| 类型 | 谁配置 | 谁承担上游成本 | 计费建议 |
|---|---|---|---|
| 平台 Key | 管理员 | 平台 | 扣用户积分/套餐 |
| 用户 BYOK | 用户 | 用户 | 可不扣上游成本，只扣服务费或不扣 |
| 混合模式 | 管理员 + 用户 | 取决于 route | 需要明确优先级 |

后续需要避免：

- 用户用自己的 Key，却被按平台 Key 成本结算。
- 平台 Key 兜底被无提示使用。
- 同一个供应商在管理员中心和用户设置页显示口径不一致。

---

## 6. 健康状态维度

健康状态不能只看供应商级别。建议拆成四层：

| 层级 | 作用 |
|---|---|
| Provider Health | 供应商整体是否异常 |
| Provider Model Health | 某个供应商模型是否异常 |
| Route Health | 某条平台供应路径是否异常 |
| Key Health | 某个 Key 是否异常、冷却、限流 |

示例：OpenAI 文本正常，但图片 429；这种情况不能简单标记 OpenAI 整体不可用。

---

## 7. 扫描与发布原则

每日扫描是合理的，但扫描结果不能直接影响线上。

推荐流程：

```text
扫描供应商模型
  -> 写入 discovered
  -> 对比新增/删除/价格/参数变化
  -> 生成变更提醒
  -> 管理员审核
  -> smoke test
  -> 绑定 canonical model 或新建 canonical model
  -> 发布到工作台
```

扫描结果不得自动：

- 发布新模型
- 删除线上模型
- 修改计费价格
- 改 route 优先级
- 替换默认模型

---

## 8. 管理员审计

以下操作应写审计日志：

- 新增/修改/删除供应商 Key
- 冷却或恢复 Key
- 启用/停用供应商
- 启用/停用模型
- 发布/下架 canonical model
- 修改 route 优先级
- 修改 fallback 策略
- 修改价格或计费 SKU
- 执行 smoke test

审计信息至少包含：

- 操作人
- 操作时间
- 变更对象
- 变更前/后摘要
- 来源页面
- 失败原因

---

## 9. Smoke Test 与探活

只保存 Key 不代表供应商可用。建议逐步补：

| 测试类型 | 说明 |
|---|---|
| 测试连接 | 验证 Key 和基础 endpoint |
| 测试模型 | 验证 provider model 可调用 |
| 测试 route | 验证 canonical model 到 provider route 的完整链路 |
| 测试计费 | 验证 usage/billing 是否记录正确 |

供应商中心应显示：

- 最后测试时间
- 最后测试结果
- 错误摘要
- 是否允许发布

---

## 10. 控制台链接与区域

供应商链接不应只有一个官网。建议支持：

- 官网
- 控制台
- 文档
- 价格页
- region/project 专属控制台
- 模型文档链接

尤其是火山方舟、腾讯云、Google Vertex 这类供应商，region/project 会影响控制台路径和实际 endpoint。

---

## 11. 工作台展示原则

工作台不应直接暴露复杂供应商概念。

工作台应该读取：

- 固定能力入口：文、图、视频、3D、音乐
- 已发布 canonical model
- 必要的模型标签和限制

供应商 route、优先级、Key 池、兜底策略应留在管理员侧。只有用户 BYOK 模式下，才需要让用户感知“我正在使用哪个供应商凭据”。

---

## 12. 建议实施顺序

### P0：状态口径补齐

- 在 `providerCatalog` 增加供应商能力状态字段。
- 供应商中心展示：展示中、可配 Key、后端已接、平台 Key 已接、BYOK 可用、待 smoke test。
- 不改执行链路。

当前状态（2026-07-15）：已落地 `capabilityStatus`，并在供应商中心卡片和详情头部显示状态矩阵。Smoke test 仍为待接入状态。

### P1：模型/Route 状态补齐

- 给 provider model 和 route 增加更明确状态。
- 供应商中心 Models / Routes 显示状态、是否发布、是否验证。
- 方舟 endpoint 映射状态单独标记。

当前状态（2026-07-15）：已落地 `ProviderModel.status` 与 `ModelRoute.executionStatus`，供应商中心 Models / Routes 已显示“已验证 / 待测试 / 需映射”和“平台可用 / BYOK / 待后端 / 停用”等只读状态。策略编辑、发布开关和 smoke test 写回仍待后续。

### P2：Smoke Test

- 先做只读/手动触发测试。
- 写入最后测试时间和错误摘要。
- 不自动发布模型。

当前状态（2026-07-15）：已落地 Key 级手动 Smoke Test 第一版。管理员可在供应商中心对单个平台 Key 触发测试；后端只校验最低凭证字段并写入 provider key health event，不调用真实上游、不自动发布模型。模型级和 Route 级真实探活待后续接入。

### P3：发布开关

- 管理员勾选 canonical model 发布到工作台。
- 工作台只读取 published catalog。
- 保留 registryId 兼容，再逐步迁到 canonicalModelId。

当前状态（2026-07-15）：已落地发布开关的配置层第一版。`ModelOpsConfig.publishedCanonicalModelAllowlist` 可按 canonical model id 收敛工作台文本/生图模型清单；远端 JSON 会过滤未知 id，全部未知时回退为不限制，避免误配置清空工作台。当前仍未提供供应商中心内的可视化勾选与持久化，也未改变任务提交的 registryId 兼容路径。

补充进展（2026-07-15）：已落地发布开关的管理闭环第一版。auth-api 新增公开读取 `/api/model-ops-config` 与管理员读写 `/api/admin/model-ops-config`，供应商中心增加工作台模型发布勾选区，可保存 `publishedCanonicalModelAllowlist` 并由工作台默认读取。当前存储为磁盘 JSON 兜底，暂未做 Postgres 共享表、逐模型审计 diff 展示和 canonicalModelId 提交链路。

补充进展（2026-07-15）：后端发布校验第一版已接入 AI Gateway 创建入口。`/api/ai/jobs` 与旧 `/ai-gateway/jobs` 在创建任务前读取 model-ops 配置；当 `publishedCanonicalModelAllowlist` 存在时，不在白名单里的 `model` / `registryId` / `metadata.canonicalModelId` 会被拒绝并返回 `AI_GATEWAY_MODEL_NOT_PUBLISHED`。当前仍兼容未配置白名单的本地/旧链路，尚未迁移到全量 canonicalModelId 提交与 route/key 可执行校验。

补充进展（2026-07-15）：前端提交 canonicalModelId 第一版已接入。`createAiJob` 会从 `canonicalModelId` / `registryId` / `model` 及 input 内同名字段解析 canonical model，并补写顶层 `canonicalModelId`、`registryId` 和 metadata；图片、即梦视频、Tripo 3D 平台 Key 路径已显式携带默认模型。后端仍保留旧字段兼容，下一步应继续做 route/key 可执行性校验。

补充进展（2026-07-15）：后端 route/key 可执行性校验第一版已接入。AI Gateway 创建入口会在发布校验后继续确认 canonical model 是否有后端可执行 route；方舟豆包/Seed、腾讯混元、OpenAI 图文等“目录存在但 Gateway adapter 未接”的模型会返回 `AI_GATEWAY_MODEL_ADAPTER_PENDING` 或 `AI_GATEWAY_MODEL_ROUTE_NOT_FOUND`，Tripo/即梦这类平台 Key 路径会在缺少可用 Key 时返回 `AI_GATEWAY_PROVIDER_KEY_UNAVAILABLE`。当前可执行 route 清单是服务端最小运行时目录，后续应继续和前端 `modelRouteCatalog` 做共享/生成化。

补充进展（2026-07-15）：route 可执行状态前后端对齐第一版已接入。新增 `shared/aiGatewayModelRoutes.js` 作为 AI Gateway runtime route 共享规则；后端 `model-route-guard` 和前端 `modelRouteCatalog` 均从该规则解析 Gateway 状态。供应商中心 Routes 行新增 `Gateway 可执行 / Gateway 待接 / 非 Gateway` 徽标，原有 `平台可用 / BYOK / 待后端` 继续表达供应商能力，避免把 BYOK 误判为平台后端已接。

### P4：后端执行对齐

- 按供应商逐个接 platform key route。
- 每接一个供应商补 adapter 测试、计费测试、健康事件。
- 不一次性全切。

### P5：扫描与变更提醒

- 接入每日扫描。
- 仅生成 discovered/变更提醒。
- 管理员审核后才发布。

---

## 13. 下一轮建议

下一轮建议优先做 **P0：供应商能力状态矩阵**。

目标：

- 不改变真实调用链。
- 在供应商中心清楚标识“展示了什么、后端接了什么、平台 Key 能不能用、BYOK 能不能用”。
- 避免产品和运营误判当前接入程度。
