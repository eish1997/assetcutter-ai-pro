# 本地伴侣：主程序与插件规范（存储 · 计算 · 站点中转 …）

本文定义 **本地伴侣（Companion）** 作为用户本机上的**主程序**，以及其下 **存储、计算、站点中转等可扩展插件** 的边界与协作方式，便于后续持续接入开源工具、仓库能力与更多本机能力。

**产品与技术已决（含历史选项对照）**：[`本地伴侣-待决策清单与建议.md`](./本地伴侣-待决策清单与建议.md)。**错误码占位**：[`附录-伴侣错误码.md`](./附录-伴侣错误码.md)。

---

## 0. 产品定位（架构决策）

| 概念 | 说明 |
|------|------|
| **本地伴侣（主程序）** | 单一产品形态：**一个安装包**、统一入口；**交付体验**为 **系统托盘必选 + 主窗口可选**（安装向导、卸载入口、**默认不开机自启**、向导内可勾选）。**首版安装包壳：Electron**，内嵌/启动现有 **Node** 宿主（与 `local-companion` 协议一致）；验证期仍可直接跑 Node + 浏览器控制台。另可演进 **Windows 服务 / 守护进程** 等企业形态。**默认仅监听 `127.0.0.1`**；**安装包正式版**：**Origin 白名单 + 配对 Token**（与现有 auth-api / bridge 设备会话对齐，见已决清单 §3）。用户只感知「装了一个本地伴侣」。 |
| **插件（能力模块）** | 在 Companion **进程内**以模块或子包实现（后续也可演进为子进程，由宿主拉起）；每个插件有 **id、semver、健康检查、能力声明**；**可单独开关**，未启用则不加载或仅注册元数据。 |
| **站点中转（Relay 插件）** | 原「本地中转」能力：**经云端 WSS 与你们后端会话**，驱动本机浏览器（CDP 等）操作**白名单目标站点**，回传消息。详细协议与连接器见 [`本地中转应用开发文档.md`](./本地中转应用开发文档.md)——该文档定位为 **Relay 插件专篇**，不再描述独立「中转应用」产品。 |
| **存储（Storage 插件）** | 本机大文件、`AssetHandle`、版本化目录与 `manifest`；为日后仓库管理预留 `catalog`。 |
| **计算（Compute 插件）** | `Job` + `ComputeAdapter` 注册表，承接接缝修等非大模型重算。 |
| **后续扩展** | 新能力 = **新插件**（或新 Adapter），接入同一套 **capabilities 宣告** 与宿主生命周期，避免再拆第二个本机常驻程序。 |

**非目标**：不要求用户分别安装「中转」「伴侣」两个互不知情的后台程序；旧文档中「可合并」的表述，**现以「中转并入伴侣」为正式结论**。

## 1. 设计原则（必须遵守）

| 原则 | 说明 |
|------|------|
| **宿主稳定、插件快更** | 宿主负责端口、认证、插件注册与生命周期；各插件可高频发版（尤其站点连接器与开源工具适配）。 |
| **协议版本化** | 对外 JSON（含 WSS 业务载荷、REST Job、AssetHandle）带 **`protocolVersion`**；破坏性变更升主版本。 |
| **能力协商** | `GET /v1/capabilities` 返回 **宿主 + 各已启用插件** 的能力与版本（如 `storage`、`compute`、`relay.site_automation`）；网站只调用已声明能力。 |
| **插件边界清晰** | 插件之间 **禁止** 隐式全局耦合；需共享能力时通过 **宿主提供的接口**（如只读配置、统一日志）注入。 |
| **存储与计算解耦** | 计算任务 **只引用** `AssetHandle` / 宿主解析后的安全路径，不魔法 cwd。 |
| **计算插件化注册** | 每个开源工具/算法封装为 **ComputeAdapter**，统一注册表。 |
| **最小信任** | 本机对外监听以 **`127.0.0.1`（或本机命名管道）** 为主；**Origin 白名单 + 配对令牌**；拒绝任意绝对路径写读。 |
| **可观测** | 每个 Job / 每条中转任务有稳定 id、阶段、结构化错误码；日志可落盘。 |

## 3. 本机目录结构（建议）

> Companion 独立仓库或 monorepo 子包；与网站前端通过 **OpenAPI / JSON Schema / `pkg/protocol`** 对齐类型。

```text
companion/
  cmd/                          # 宿主入口：daemon / tray
  internal/
    api/                        # 统一 HTTP + WS、/v1
    auth/
    pluginhost/                 # 插件注册、依赖注入、capabilities 聚合
    telemetry/
    plugins/
      storage/                  # 存储插件
        volume/
        layout/
        manifest/
        catalog/                # 【预留】仓库索引
      compute/                  # 计算插件
        registry/
        runner/
        adapters/
          seam_repair/
          ...
      relay/                    # 站点中转插件（原「本地中转」）
        transport/              # 与云端 WSS（可由插件持有或宿主注入）
        orchestrator/
        session/
        security/
        connectors/             # 原 community / overrides / manifest
            community/
            overrides/
            manifest.json
  pkg/protocol/
```

**依赖建议**：`api` → `auth` → `pluginhost`；各 `plugins/*` 向 `pluginhost` 注册；**禁止** `storage` → `compute` 直接引用；Relay 与 Storage 默认 **无直接依赖**（若未来需要「中转结果落盘」，经宿主协调或显式 API）。

## 4. 资源抽象（存储插件 · 本期薄实现 + 预留仓库）

### 4.1 核心类型

`VolumeId`、`ProjectId`、`AssetHandle`、`UriRef` —— 网站持久化 **仅 `AssetHandle`**，不存绝对路径。

**AssetHandle** 示例：

```json
{
  "protocolVersion": 1,
  "kind": "companion.v1.asset",
  "volumeId": "default",
  "scope": "project",
  "projectId": "<uuid>",
  "key": "<uuid 或 content-address>",
  "relPath": "assets/<key>/model.glb",
  "byteSize": 12345678,
  "mime": "model/gltf-binary",
  "sha256": "可选"
}
```

### 4.2 目录布局（`layoutVersion`）

```text
<volumeRoot>/
  projects/<projectId>/
    manifest.json
    assets/<key>/
      original.bin
      sidecar/
    scratch/<jobId>/
```

**manifest.json（P0 建议字段）**：

```json
{
  "layoutVersion": 1,
  "updatedAt": 1710000000000,
  "entries": [
    {
      "key": "...",
      "relPath": "assets/.../model.glb",
      "byteSize": 0,
      "tags": [],
      "lineage": null
    }
  ]
}
```

**并发（P0 假设，须在实现 README 写明）**：单进程内 **单写者** 更新 `manifest.json`；若未来多进程/多线程写同一项目，需引入 `manifestEtag` / 文件锁（P1）。

### 4.3 Storage API（HTTP 草案）

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/v1/capabilities` | 聚合宿主 + **各插件**能力、版本、`layoutVersion`、配额 |
| `POST` | `/v1/storage/session` | 可选：分块上传会话 |
| `PUT` | `/v1/projects/:projectId/assets/:key` | 单文件上传 |
| `GET` | `/v1/projects/:projectId/assets/:key` | 读取已落盘 object 原始字节；`Content-Type` 取自 manifest 中该 key 的 `mime`（**`local-companion` 已实现**） |
| `GET` | `/v1/projects/:projectId/assets/:key/meta` | 元数据 |
| `DELETE` | `/v1/projects/:projectId/assets/:key` | 删除并更新 manifest |

## 5. 计算抽象（计算插件 · Job + Adapter）

### 5.1 Job 信封

```json
{
  "protocolVersion": 1,
  "jobId": "<uuid>",
  "type": "seam_repair",
  "projectId": "<uuid>",
  "inputs": [
    { "role": "mesh", "asset": { "kind": "companion.v1.asset", "projectId": "...", "key": "..." } }
  ],
  "params": {},
  "outputPolicy": { "writeScratch": true, "promoteToAsset": false }
}
```

### 5.2 ComputeAdapter（每个开源工具一个实现）

| 项 | 说明 |
|----|------|
| `id` | 如 `seam_repair@v1` |
| `semver` | 适配器版本 |
| `declaredCaps` | GPU / 内存上限 / 是否联网 |
| `validate(job)` / `run(job, ctx)` / `health()` | 语义同前 |

**注册**：由计算插件在启动时加载 `adapters/*`（实现语言与宿主一致即可，不限定 Go）。

### 5.2.1 开源能力接入策略（通用，新增）

> 结论：**优先“调用开源项目”而非“直接修改开源项目源码”**。  
> 宿主负责稳定协议与资产编排，开源项目负责具体算法或执行。

#### 推荐形态（默认）

1. 在 `adapters/*` 新增一个 ComputeAdapter（如 `xxx@v1`）。  
2. Adapter 通过 **HTTP / 子进程 / SDK** 调用开源能力。  
3. 输入与输出统一走 `Job` 与 `AssetHandle`，结果写回本地仓库。  
4. 网站仅调用 `companionClient`，不直接依赖开源项目内部细节。

#### 何时允许改开源源码

- 上游存在阻断性 bug，必须修复才能跑通。  
- 业务刚需能力无法通过外部参数或封装实现。  
- 性能瓶颈必须深入内核优化。

若需要改，建议：**fork + 最小改动 + 记录补丁**（改动点、原因、回滚方案）。

#### 对网站开发者的意义（大白话）

- 网站前端只管“收输入、提任务、展示结果”。  
- 本地伴侣只管“把任务交给适配器、拿回结果、存资产”。  
- 开源项目可升级可替换，网站交互层基本不受影响。

### 5.3 进度（当前实现 + 草案）

- **已实现（P0.5）**：`GET /v1/compute/jobs/:jobId/events?afterSeq=&limit=`，事件含 `seq`，可做轮询增量拉取。  
- **已实现（宿主）**：`GET /v1/compute/jobs/:jobId/stream`（SSE，`job.event` / `job.end`）；主站可 **SSE 优先、失败回退轮询**。  
- **目标（P1）**：按需升级为 **WS** 或与 Relay 统一的实时通道，降低长连与鉴权边缘情况成本。

### 5.4 提交计算任务（HTTP 草案，与 §5.1 信封对应）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/v1/compute/jobs` | body 为 §5.1 Job 信封（或由宿主包装一层 `{ "job": {...} }`）；返回 `{ "jobId" }` |
| `DELETE` | `/v1/compute/jobs/:jobId` | 取消（尽力而为） |

（具体状态码、错误体与 `protocolVersion` 对齐方式：**P0 落地时在 `pkg/protocol` 定稿**。）

## 6. 站点中转插件（Relay）边界

- **协议与连接器**：见 [`本地中转应用开发文档.md`](./本地中转应用开发文档.md)（WSS 任务 envelope、`SiteConnector` 形状、`bb-sites` 策略等）。

- **与网站关系**：网站经 **你们后端** 将任务路由到 **已配对设备上的 Companion**；Companion 内 **Relay 插件**执行具体站点逻辑。

## 7. 网站侧模块化（与宿主对齐）

**已实现（P1 演进中）**：主站 **`services/companionClient/`**（`probe`、`storage`、`compute`、`fetch`）；与下表对应。长期仍可抽为 **`packages/companion-client`**。

| 模块 | 职责 |
|------|------|
| `probe.ts` | 探测宿主、`protocolVersion`、**聚合 capabilities** |
| `storage.ts` | 存储插件 API（`GET /v1/projects`、manifest、**`GET` 资产二进制**（`fetchCompanionAssetBlob`）、asset meta 等） |
| `compute.ts` | 提交 Job / 列表与查询；**`submitCompanionSeamRepairJob`**（轮询；WS 进度为 P1） |
| `relay.ts` | 从 **`/v1/capabilities.relay`** 读中转切片（**M1**）；与后端 WSS 协同仍为后续 |
| `types.ts` / `policy.ts` | 同源类型与降级策略（占位见 `types/companion.ts`；**P1** 扩 `policy`） |

业务代码 **不** 直连各插件内部 URL 碎片。

## 8. 安全清单（宿主 + 插件）

- [ ] 本机监听范围与防火墙策略文档化（**已决**：默认 **`127.0.0.1` 仅本机**；局域网调试用单独「开发模式」开关，见已决清单）  
- [ ] Origin 白名单 + 配对 token + 可撤销（**已决**：**开发构建可宽**；**Electron 安装包版**收紧白名单 + Token，与 bridge 对齐）→ **进行中（宿主）**：`COMPANION_ALLOWED_ORIGINS` + `COMPANION_SHARED_TOKEN` + 主站 `companionClient` Bearer；**可撤销 / 设备级会话** 待后端。  
- [ ] 路径：仅 `volumeRoot + relPath` 规范化校验（`local-companion` 已对 `projectId`/`key` 做安全子集校验，持续补强）  
- [ ] ComputeAdapter 默认无网；Relay 仅白名单站点  
- [ ] Job / 中转任务：超时、取消、并发与磁盘上限（**已决**：**P1** 与 scratch TTL/磁盘上限一并落地）  

**已知限制（产品文案，已决）**：若用户自 **HTTPS 生产站** 访问本机 **HTTP 伴侣**，部分企业环境会拦截混合内容或本机回环；界面提示：*「当前网络或安全策略可能阻止浏览器访问本机伴侣，请检查企业代理 / 防火墙或联系管理员」*（技术绕行方案 **P1** 再评估）。

## 9. 演进路线（建议）

| 阶段 | 宿主 | 存储 | 计算 | Relay |
|------|------|------|------|-------|
| **P0** | 单进程 + pluginhost + `/v1/capabilities` | 单 Volume + manifest | 1 个 Adapter | 1 站点打通 |
| **P1** | 插件热开关、结构化错误码统一 | 分块上传、sha256 | 多 Adapter、取消 | 流式、多连接器 |
| **P2** | 可选子进程隔离重型插件 | catalog | 沙箱 | `bb-sites` 灰度与回滚 |

> 面向最终产品闭环：P1 结束时需满足「网站可见流式进度 + 断线恢复 + 用户可见故障提示」三件套。

## 10. 结论

- **本地伴侣 = 主程序**；原「本地中转」= **Relay 插件**，与 **Storage / Compute** 并列，后续能力继续以 **插件** 扩展。  
- **规范化** = 宿主 **capabilities** + **protocolVersion** + **AssetHandle** + **Job 信封** + **各域注册表**（连接器 / ComputeAdapter）。  
- 站点细节仍以 [`本地中转应用开发文档.md`](./本地中转应用开发文档.md) 为 **Relay 插件**的深入规格，但总架构与目录归属 **以本文为准**。

**产品安装形态（已决，2026-04-27）**：[`本地伴侣-待决策清单与建议.md`](./本地伴侣-待决策清单与建议.md) §1～§3。

## 11. 执行就绪（与团队 B 对齐：能否开干 + 建议）

### 11.1 结论：**可以开始执行**，但须先选 **一条垂直切片**

文档已足够启动 **架构落地 + 单插件 MVP**；**不建议** P0 首迭代同时满配「宿主 + Storage + Compute + Relay」四条线并行，除非人力明确拆分。

| 推荐首切片 | 内容 | 说明 |
|------------|------|------|
| **切片 A（延续现有资产）** | 以仓库内 **`A-Driver` / `local-bridge`** 为 **Relay 可运行子工程**，协议与本文对齐；目录命名逐步迁往 `plugins/relay` | 最快见链路；与历史纪要一致 |
| **切片 B（新宿主壳）** | 新建 **Companion 最小进程**：仅 `api` + `auth` + `pluginhost` + `GET /v1/capabilities`；**Relay 作为唯一已启用插件** | 长期形态正；首周工作量大 |
| **切片 C（存储优先）** | 宿主壳 + **Storage 插件** + 网站 `companion-client` 探测；Relay 二期 | 适合先做工作区大文件落盘 |

**团队 B 开干前 1 次决策会**（约 30 分钟）：选定 A/B/C、技术栈、默认监听 **端口或端口范围**、是否与现有 `A-Driver` 仓库合并。
