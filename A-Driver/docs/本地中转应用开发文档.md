# 本地中转应用开发文档（MVP）

## 1. 目标与范围

目标是实现“网站输入 -> 本地执行 -> 网站回传”的闭环链路，支持多站点插件化，首期至少支持 `gemini-web`。

本期范围：

- 本地中转应用核心骨架：`transport`、`orchestrator`、`plugin-runtime`
- 统一 connector 接口 + 至少 1 个示例 connector
- 任务事件链路：`task.send_message` -> `reply.delta`/`reply.completed`
- 错误分类与全链路日志（带 `taskId`）
- 可运行说明 + 验证步骤（成功与失败用例）

本期非目标：

- 一次性支持全部目标站点
- UI 大改
- 与当前链路无关的大规模重构

## 2. 硬性约束

- 安全：本地服务仅监听 `127.0.0.1`，云端通信必须 `WSS/TLS`
- 解耦：通用核心不得硬编码站点选择逻辑
- 回滚：适配器更新失败必须回退到上一版本
- 可观测：每个任务日志必须包含 `taskId`
- 可测试：至少 1 条自动化测试覆盖关键链路

## 4. 总体架构

```text
网站前端
  │ HTTPS/WSS
网站后端（鉴权、任务路由）
  │ WSS
本地中转应用（用户电脑）
  ├─ transport（连接云端）
  ├─ orchestrator（任务编排）
  └─ plugin-runtime（connector 运行时）
      ├─ community（bb-sites）
      └─ overrides（私有兜底）
```

标准链路：

1. 网站后端下发 `task.send_message`
2. `transport` 验签并 ACK，交由 `orchestrator`
3. `orchestrator` 选择 connector 并执行 `sendMessage`
4. connector 通过 `subscribeReplies` 推送增量内容
5. `transport` 回传 `reply.delta`/`reply.completed` 或 `task.failed`

## 5. 协议设计

统一 envelope：

```json
{
  "type": "task.send_message",
  "taskId": "uuid",
  "connectorId": "gemini-web",
  "payload": {
    "text": "用户输入内容"
  }
}
```

必选事件：

- `task.accepted`
- `reply.delta`
- `reply.completed`
- `task.failed`

建议补充事件：

- `transport.disconnected`
- `task.timeout`
- `connector.unhealthy`

### 5.1 设备鉴权与会话字段（建议固定）

握手阶段建议至少包含以下信息：

- `Authorization: Bearer <deviceSessionToken>`
- `x-a-driver-device-id: <deviceId>`
- （可选）`x-a-driver-client-version: <semver>`

约束建议：

- `deviceSessionToken` 由网站后端签发，必须带过期时间（如 24h）
- token 过期后由本地中转触发刷新流程（静默刷新失败再要求重新配对）
- 后端以 `deviceId + userId` 做绑定校验，拒绝跨用户复用设备 token

### 5.2 任务幂等与重复消息规则

后端与本地中转均按 `taskId` 做幂等，建议规则如下：

- 若 `taskId` 首次到达：正常受理，回传 `task.accepted`
- 若 `taskId` 重复且仍在执行中：返回当前状态（不重复执行）
- 若 `taskId` 重复且已完成：可回放最近一次 `reply.completed`（或返回 `task.duplicate`）
- 幂等窗口建议保留最近 N 分钟（如 10~30 分钟）的 `taskId` 记录

### 5.3 传输层 messageId、去重与 ACK

- 服务端下发 `task.send_message` 时携带 **`messageId`**（UUID）；调用方也可在 `POST /api/bridge/tasks/send-message` 的 body 中传入同一 `messageId` 以实现「业务层重试不重复投递」。
- 服务端在窗口内（默认 30 分钟，可调 `BRIDGE_DISPATCH_DEDUP_MS` / `BRIDGE_DISPATCH_DEDUP_MAX`）对 **`deviceId + messageId`** 去重：重复请求返回 `deduped: true`，不再次推送到 WebSocket。
- 设备收到带 `messageId` 的任务后，应尽快上行 **`transport.ack`**（含 `messageId`、`taskId`、`receivedAt`），便于服务端观测与对账。
- 任务事件流中可同时看到 `task.dispatched` 与 `transport.ack`。

## 6. Connector 统一接口

```ts
export interface SiteConnector {
  id: string;
  version: string;
  match(ctx: { connectorId?: string; domain?: string }): boolean;
  init(ctx: ConnectorContext): Promise<void>;
  sendMessage(input: SendInput): Promise<{ requestId: string }>;
  subscribeReplies(cb: (event: ReplyEvent) => void): () => void;
  healthCheck(): Promise<HealthResult>;
  teardown(): Promise<void>;
}
```

约束说明：

- `match` 只做选择判断，不做业务副作用
- `init` 可重入，失败需返回可分类错误
- `subscribeReplies` 必须返回取消订阅函数
- `teardown` 必须释放监听器与资源句柄

## 7. 核心模块职责

### 7.1 transport

- 建立 `WSS` 长连接、心跳、自动重连
- 消息 ACK 与重复消息去重
- 连接状态变化事件上报

### 7.2 orchestrator

- 任务队列、并发控制、超时与重试
- 任务状态机（accepted/running/completed/failed）
- 将 connector 异常映射为统一错误码

### 7.3 plugin-runtime

- 加载社区插件与私有 override
- 按 connector 优先级进行路由
- 版本切换失败自动回滚

优先级建议固定为：

1. `overrides`（私有兜底）
2. `community`（bb-sites 同步）

说明：当同一 `connectorId` 在两侧均存在时，一律命中 `overrides`，避免线上修复被社区版本覆盖。

### 7.4 telemetry

- 结构化日志（至少包含 `taskId`、`connectorId`、`event`）
- 错误统计（按错误码聚合）
- 健康检查结果上报

## 8. 错误码与可观测性

建议错误码：

- `E_SITE_NOT_LOGGED_IN`：目标站点未登录
- `E_TRANSPORT_DISCONNECTED`：连接断开
- `E_CONNECTOR_RUNTIME`：适配器运行异常
- `E_TASK_TIMEOUT`：任务超时
- `E_CONNECTOR_NOT_FOUND`：未找到可用 connector

日志示例（JSON）：

```json
{
  "level": "error",
  "taskId": "t-123",
  "connectorId": "gemini-web",
  "code": "E_TASK_TIMEOUT",
  "message": "task exceeded timeout",
  "ts": "2026-04-16T10:00:00.000Z"
}
```

## 9. 运行配置建议

可配置项：

- 网站后端 WS 地址：`wss://your-domain/...`
- 设备配对方式：`扫码` 或 `一次性口令`
- 首批目标站点：`gemini-web`
- 运行时：`node`（MVP 推荐）
- 最小支持系统：`Windows 10+`

安全默认值：

- 本地监听地址：`127.0.0.1`
- 禁止明文 WS
- 仅允许白名单 connector 加载

## 9.1 bb-browser 调用约定（MVP）

为避免不同 connector 行为不一致，MVP 建议统一：

- 默认命令：`npx -y bb-browser site <route> <text> --json`
- `route` 解析顺序：
  1. `task.send_message.payload.threadId`（若约定为 route 覆盖）
  2. 环境变量 `BB_BROWSER_SITE_ROUTE`
  3. 兜底默认值（如 `wikipedia/summary`）
- `stdout` 作为主要结果来源；非空 `stderr` 且退出码非 0 视为失败

错误映射建议：

- `command not found` / 启动失败 -> `E_CONNECTOR_RUNTIME`
- 退出码非 0 且提示未登录/鉴权失败 -> `E_SITE_NOT_LOGGED_IN`
- 超时 -> `E_TASK_TIMEOUT`

## 10. 本地运行步骤

1. 安装依赖并启动本地中转应用
2. 完成设备配对，获取可用设备会话
3. 配置 `WSS` 地址与认证信息
4. 启动后确认日志输出 `connected`
5. 在网站发起一次 `task.send_message`
6. 观察回传事件：`task.accepted` -> `reply.delta` -> `reply.completed`

## 11. 验证步骤（含成功/失败）

成功用例：

- 用例 S1：`gemini-web` 正常发送并收到流式回传
- 预期：前端可实时看到增量文本，最终收到 `reply.completed`

失败用例：

- 用例 F1（未登录站点）：触发 `E_SITE_NOT_LOGGED_IN`
- 用例 F2（断网/断连）：触发 `E_TRANSPORT_DISCONNECTED`，自动重连后恢复
- 用例 F3（超时）：触发 `E_TASK_TIMEOUT`，任务结束为 failed
- 用例 F4（适配器异常）：触发 `E_CONNECTOR_RUNTIME`，记录堆栈摘要

自动化测试最低要求：

- 覆盖 1 条关键链路：任务进入队列后，超时分支可正确产出 `task.failed`

## 13. 已知限制与后续建议

已知限制：

- DOM 适配依赖目标站点结构，站点改版会导致 connector 失效
- 用户本机环境差异会影响稳定性（浏览器版本、权限、网络）

后续建议：

- 建立 connector 兼容性矩阵与自动回归
- 增加灰度发布与插件签名校验
- 引入更细粒度的重试策略与退避机制
